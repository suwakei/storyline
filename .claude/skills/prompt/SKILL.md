# /prompt — Claude Code 作業指示プロンプト生成スキル

曖昧な「やりたいこと」を受け取り、意図を把握し、**Claude Code に渡せる洗練された作業指示プロンプト**に仕上げて出力する。
ドラフトを一発で確定させず、**提示 → 確認 → 改善のループ**でユーザーと磨き上げてから最終プロンプトを渡すのがこのスキルの核。

> **このスキルはプロンプトを生成するだけ。タスク自体は実行しない。**
> 生成したプロンプトを使うかどうか・実行するかどうかはユーザーが決める。

このスキルは特定プロジェクトに依存しない。どのリポジトリ／リポ外でも動作する。

---

## 入力

- 起動形式: `/prompt <やりたいこと>`
- **引数あり** → その自由文を「やりたいこと」として扱う。
- **引数なし** → まず「どんなプロンプトを作りたいですか？やりたいことを教えてください」と1問だけ聞いてから開始する。

## 出力

- **プロンプト本体**: コードブロック（```）で囲んでそのままコピペできる形で返す。
- **簡単な補足**: コードブロックの外に、確認した前提・使い方の一言を2〜4行で添える。
- **出力言語は入力に合わせる**。やりたいことが日本語なら日本語、英語なら英語でプロンプトを生成する。
- **ファイルには保存しない**（表示のみ）。
- **ドラフトを提示 → 確認 → 改善のループ**で磨き、ユーザーが「確定」したものを最終プロンプトとする。

---

## ワークフロー

### Step 1. 意図の把握
やりたいことを読み、何を達成したいのかを掴む。

### Step 2. 曖昧さの判定
Claude Code の作業指示として成立するために必要な以下の軸をチェックし、欠けている／曖昧な軸を洗い出す。

1. **目的／ゴール** — どんな成果・終状態を求めているか
2. **対象範囲・対象ファイル/モジュール** — どこを触るのか
3. **守るべき制約・規約** — 触ってはいけない箇所、従うべきルール
4. **受け入れ基準・検証手段** — テスト、動作確認、完了の定義
5. **期待アウトプットの形式** — 差分／PR／説明 など

判定基準:
- **十分明確** → 質問せず Step 4 へ直行する。
- **曖昧** → Step 3 へ。特に **1（目的）・2（対象）** が不明なときは必ず確認する。

過剰な質問は避ける。明確なものをわざわざ聞き返さない。

### Step 3. 明確化（曖昧なときだけ）

1. **コードベース調査（`context-scout` を Explore に委譲）**: 依頼にファイル名・機能名が出ていて実コードの裏付けが要るとき、[`agents/context-scout.md`](agents/context-scout.md) を Read し、その内容＋入力（request / unknowns / repo_root）をタスクプロンプトとして **`Agent` ツールで `subagent_type: Explore`（read-only 調査エージェント）を起動**する。Explore は Edit/Write を構造的に持たないため、調査が read-only であることがツールレベルで担保される（プロンプト文言だけに頼らない）。エージェントは対象パス・既存パターン・テスト/検証コマンド・規約・影響範囲の**ダイジェスト**を返すので、それをプロンプトに反映する。これで曖昧さが解消できるなら質問は省く。
   - 軽微な確認（1ファイル見れば済む等）は委譲せずインラインの Read/Grep でよい。リポジトリ外なら調査はスキップ。
2. **選択式で聞く**: 残った曖昧な軸について、`AskUserQuestion` で選択肢を提示する（1ラウンド最大3問程度に絞る）。各設問は妥当な選択肢＋「Other（自由記述）」で構成する。
3. **記述式にフォールバック**: 選択肢では捉えきれない／回答後もまだ特定できない場合は、的を絞った自由記述の質問を1つ追加する。

明確化が済んだら Step 4 へ。

### Step 4. ドラフト生成
把握した意図をもとに、Claude Code 作業指示プロンプトの**ドラフト**を生成する。**構造は依頼に応じて適応**させる。

1. **タスク種別を判定**する（バグ修正／機能追加／リファクタ／調査／テスト追加／一括変換／最適化／ドキュメント／レビュー 等）。
2. [`references/prompt-schemas.md`](references/prompt-schemas.md) を **Read** し、該当種別の**最適なセクション構成（スキーマ）**を適用する。複数種別にまたがる依頼は構成を合成する。
3. 不要なセクションは省き、依頼固有の情報（対象パス・受け入れ基準など）を埋める。推測したパス/規約は「要確認」と明示する。
4. 生成後、同ファイル末尾の「**品質チェック**」で自己点検してから提示する。

### Step 5. レビュー & 改善ループ（このスキルの核）
ドラフトは一発で確定させない。ユーザーに見せ、フィードバックを受けて磨き込む。**ユーザーが「確定」するまで 1〜3 を繰り返す。**

1. **提示**: 現ドラフトをコードブロックで提示し、外側に「確認した前提・残る不確実点・使い方」を簡潔に添える。曖昧なまま埋めた箇所は「ここは仮置き」と明示する。2 ラウンド目以降は**前回からの変更点を一言**添える。
2. **確認を聞く**: `AskUserQuestion` で確定/修正を確認する。選択肢の例:
   - **これで確定** — 完成。ループを抜けて Step 6 へ
   - **部分的に直したい** — 直す箇所を聞く（Other に自由記述、または次の質問で詳細化）
   - **方向性から見直したい** — 前提・構成・タスク種別の解釈から再検討
3. **反映して再生成**: フィードバックを取り込む。必要なら追加調査（`context-scout`）や追質問をしてからドラフトを更新し、**1 に戻る**。

ループの作法:
- 毎ラウンド必ず「確定でよいか」の**出口**を用意する。ユーザーはいつでも抜けられる。
- 同じ指摘で堂々巡りしない。迷う点は選択式で具体化して前に進める。
- 明確な依頼で初回ドラフトに不満が無ければ、**1 ラウンドで確定**して構わない（ループを強制しない）。

### Step 6. 確定
- 確定したプロンプト本体をコードブロックで最終提示する。
- 外側に補足（前提・使い方）を簡潔に添える。
- **タスクは実行しない**。「このプロンプトをこのまま Claude Code に渡せます」程度に留める。

## 良いプロンプトの原則

- ゴールを具体的・検証可能に書く（「良くする」ではなく「何がどうなれば完了か」）。
- 対象ファイル/パスは推測でなく、調査で確認したものを明示する。
- 守るべき制約・規約・触ってはいけない箇所を明記する。
- 受け入れ基準（テスト・動作確認の手段）を入れる。
- 複雑なら手順に分解する。冗長な前置きは避け、命令は明確に。
- プロジェクト固有の規約が判明していれば、それに従うよう指示に含める。

## やってはいけないこと

- 生成したプロンプトのタスクを**実行しない**（コード変更・コマンド実行をしない）。
- プロンプトを**ファイルに保存しない**。
- 明確な依頼に対して**不要な質問をしない**（ただし初回ドラフトの確認は必ず取る）。
- 推測でファイルパスや規約を断定しない（不確かなら調査するか、プロンプト内で「要確認」と明示する）。
- ユーザーの**確定を取らずに勝手に完成扱いしない**。提示しっぱなしで終わらず、必ず確認を聞く。

## 例

**入力**: `/prompt ログイン画面のバリデーションを直したい`

→ 目的（何がどう壊れている？）・対象（どのファイル？）・受け入れ基準が曖昧。
→ コードベースを調べてログイン画面の場所を特定しつつ、`AskUserQuestion` で「直したいのは挙動／文言／両方？」「対象は FE のフォーム検証／BE の API 検証？」を確認。
→ ドラフトをコードブロックで提示し、確認を聞く。「受け入れ基準を増やしたい」等のフィードバックを反映して再提示 → **ユーザーが確定するまでループ** → 確定したものを最終提示。

**入力**: `/prompt src/utils/date.ts の formatDate に null 安全化を入れて。引数が null/undefined なら空文字を返す。既存テストは壊さず、ケースを1つ追加`

→ 目的・対象・受け入れ基準が明確 → 質問せず即ドラフト生成 → 確認を1回取り、修正が無ければそのまま確定（1 ラウンドで完了）。
