# プロンプト構成スキーマ（タスク種別別）

> `/prompt` スキルが、依頼を**タスク種別に分類し、その種別に最適なセクション構成**で
> Claude Code 作業指示プロンプトを生成するための参照。SKILL.md の Step 4 から参照される。
>
> 使い方: ① 依頼を下の「タスク種別の見分け方」で分類 → ② 該当スキーマのセクション構成を採用
> → ③ 不要なセクションは省き、依頼に固有の情報を埋める。複数種別にまたがる依頼は構成を合成する。

---

## セクション・カタログ（構成要素）

プロンプトはこれらの「部品」から、タスクに必要なものだけを選んで組む。

| セクション | 役割 | よく使う種別 |
|---|---|---|
| **目的 / ゴール** | 何を達成すれば完了か。検証可能な終状態 | ほぼ全て |
| **背景・コンテキスト** | 前提情報、関連する既存実装、なぜやるか | 自明でないとき |
| **対象ファイル / 範囲** | 触る場所を具体パスで明示 | ほぼ全て |
| **症状 / 現状の問題** | 今どう困っているか | 修正・リファクタ・最適化 |
| **再現手順** | バグを再現する具体的ステップ | バグ修正 |
| **原因仮説** | 当たりがついていれば（任意） | バグ修正・調査 |
| **仕様 / 要件** | 期待する入出力・振る舞いの定義 | 機能追加 |
| **制約・不変条件** | 守るルール、挙動を変えない約束、規約 | ほぼ全て |
| **手順** | 作業を順序立てて分解 | 多段・複雑なとき |
| **受け入れ基準 / 完了条件** | 「終わった」と言える条件のリスト | ほぼ全て |
| **検証方法** | テスト・コマンド・動作確認の手段 | ほぼ全て |
| **期待アウトプット / 報告形式** | 成果物の形（差分／PR／報告書）と報告の仕方 | 調査・レビュー |
| **触ってはいけない範囲** | 変更禁止箇所のガードレール | 影響範囲が広いとき |

原則: **不要なセクションは入れない**。空欄の見出しを並べるより、必要な部品だけで簡潔に。

---

## タスク種別の見分け方

| 依頼の特徴 | 種別 |
|---|---|
| 「直したい」「バグ」「動かない」「エラー」 | バグ修正 |
| 「追加したい」「作りたい」「実装して」 | 機能追加 |
| 「整理」「リファクタ」「挙動はそのままで」 | リファクタリング |
| 「調べて」「原因は」「なぜ」「どうなってる」（変更を伴わない） | 調査・原因究明 |
| 「テストを書いて」「カバレッジ」 | テスト追加 |
| 「全部」「一括」「移行」「置換」「リネーム」 | 一括変換・移行 |
| 「速くしたい」「重い」「最適化」 | パフォーマンス最適化 |
| 「ドキュメント」「README」「説明を書いて」 | ドキュメント |
| 「レビューして」「指摘して」 | レビュー |
| 「設計して」「比較して」「どっちがいい」「方式を決めたい」（実装は次段） | 設計検討・技術選定 |

複数該当する場合は主たる目的の種別を軸に、必要な部品を他種別から借りる。

## 種別ごとの最適構成

各スキーマは「**採用するセクション**」と「**この種別で特に効くポイント**」を示す。
テンプレは骨格。実際の依頼に合わせて中身を埋め、不要部分は削る。

### 1. バグ修正
採用: 目的 / 症状・再現手順 / 対象（判明していれば）/ 原因仮説（任意）/ 修正方針 / 受け入れ基準 / 検証（回帰防止）/ 触らない範囲
効くポイント: **再現条件**と「**直ったと言える条件**」を最優先で明確化。再発防止のテストを受け入れ基準に含める。
```
## 目的
<何を直すか。直った状態の定義>

## 症状 / 再現手順
1. <手順>
2. <期待 vs 実際>

## 対象
<ファイル/パス。不明なら「特定から」と明記>

## 修正方針 / 原因仮説（あれば）
<当たりがあれば>

## 受け入れ基準
- [ ] <症状が解消する条件>
- [ ] 再現ケースを再発防止テストとして追加
- [ ] 既存テストが緑のまま

## 検証
<実行するテスト/コマンド>
```

### 2. 機能追加
採用: 目的 / 背景 / 仕様・要件 / 対象ファイル / 設計方針（任意）/ 制約・規約 / 受け入れ基準 / テスト
効くポイント: **入出力の仕様**を具体例で固定する。既存の規約・パターンに合わせる指示を入れる。
```
## 目的
<追加する機能と、それで何ができるようになるか>

## 仕様 / 要件
- 入力: <…>
- 出力 / 挙動: <…>
- エッジケース: <…>

## 対象ファイル
<追加/変更するパス>

## 制約・規約
<従う既存パターン、命名、触らない箇所>

## 受け入れ基準
- [ ] <機能が満たすべき条件>
- [ ] テスト追加（正常 + 異常 + 境界）
- [ ] 既存テスト緑
```

### 3. リファクタリング
採用: 目的 / 対象 / 現状の問題 / **不変条件** / 方針 / 受け入れ基準 / 検証
効くポイント: 「**外部から見た挙動を変えない**」を最重要制約として明示。検証は「既存テスト緑＋振る舞い差分なし」。
```
## 目的
<何をどう整理するか>

## 対象 / 現状の問題
<パスと、今の何が問題か>

## 不変条件（最重要）
- 外部から見た挙動・API・出力を変えない
- <その他変えてはいけないもの>

## 方針
<どう変えるか>

## 受け入れ基準
- [ ] 既存テストが全て緑（変更なし）
- [ ] 公開インターフェース不変
```

### 4. 調査・原因究明
採用: 問い / 調査範囲 / **期待アウトプット（報告）** / 制約（変更禁止）/ 参考になりそうな場所
効くポイント: 成果物は**コードでなく報告**。「コードは変更しない」を明示し、報告フォーマットを指定する。
```
## 問い
<明らかにしたいこと>

## 調査範囲
<見るべきディレクトリ/機能>

## 制約
- コードは変更しない（調査・報告のみ）

## 期待アウトプット
- 結論（要点）
- 根拠（該当ファイル:行）
- 補足/推奨アクション
```

### 5. テスト追加
採用: 対象 / カバーすべきケース / テストFW・配置規約 / 受け入れ基準 / 既存を壊さない
効くポイント: **網羅すべきケース**（正常・異常・境界）を列挙。使用フレームワークと配置場所を指定。
```
## 対象
<テスト対象の関数/モジュール>

## カバーすべきケース
- 正常系: <…>
- 異常系: <…>
- 境界: <…>

## テスト方針
<フレームワーク / 配置パス / 既存テストの書き方に合わせる>

## 受け入れ基準
- [ ] 上記ケースを網羅
- [ ] 全テスト緑
```

### 6. 一括変換・移行
採用: 対象範囲 / 変換ルール / 除外条件 / 段階実行（任意）/ 検証 / 報告
効くポイント: **対象の全範囲**と**変換ルール（before→after）**を厳密に。漏れ・誤変換を防ぐ検証と件数報告を入れる。
```
## 目的
<何を何に一括で変えるか>

## 対象範囲
<どのディレクトリ/パターン全部>

## 変換ルール
- `<before>` → `<after>`
- 除外: <変換しない条件>

## 検証
- [ ] ビルド/型チェック通過
- [ ] 全テスト緑
- [ ] 旧パターンの残存ゼロを確認

## 報告
- 変換した件数とファイル一覧
```

### 7. パフォーマンス最適化
採用: 目標指標 / 対象 / 計測方法 / 制約 / 受け入れ基準
効くポイント: **数値目標**と**計測方法（before/after）**を定義。機能・挙動を変えない制約を添える。
```
## 目的 / 目標指標
<例: 一覧APIのp95を 800ms → 300ms 以下>

## 対象
<ボトルネックと思われる箇所>

## 計測方法
<before/after をどう測るか>

## 制約
- 機能・出力結果を変えない

## 受け入れ基準
- [ ] 目標指標を達成
- [ ] 既存テスト緑
```

### 8. ドキュメント
採用: 目的 / 読者 / 対象 / 形式・配置 / 含める内容 / 既存スタイル
効くポイント: **読者**と**形式・配置場所**を指定し、既存ドキュメントのスタイルに合わせる。
```
## 目的 / 読者
<誰向けの、何のための文書か>

## 対象 / 配置
<書く内容の対象、出力するパス>

## 含める内容
- <項目1>
- <項目2>

## スタイル
<既存ドキュメントのトーン/構成に合わせる>
```

### 9. レビュー
採用: 対象 / 観点 / 重大度の基準 / 出力形式 / 修正の有無
効くポイント: **観点**と**出力形式（指摘リスト）**を指定。「修正までするか／指摘だけか」を明確化。
```
## 対象
<diff / PR番号 / ファイル>

## 観点
<バグ / 設計 / 規約 / パフォーマンス など>

## 出力形式
- 指摘ごとに: 重大度 / 場所(file:line) / 問題 / 提案

## スコープ
- 指摘のみ（修正はしない）／ または修正まで行う
```

### 10. 設計検討・技術選定
採用: 問い / 目的 / 評価基準（軸）/ 候補案（2〜3案）/ 各案のトレードオフ / 推奨と理由 / 未決事項 / 制約（実装しない）
効くポイント: 成果物は**コードでなく設計提案**。「この段階では実装しない（提案のみ）」を明示し、**評価軸を先に固定**して全候補を同じ軸で比較する。調査（既存把握）と違い、**前向きに選択肢を作って薦める**のが主眼。
```
## 問い / 目的
<決めたいこと。何を選ぶか / どう設計するか>

## 評価基準（軸）
- <例: 実装コスト / 既存構成との整合 / 拡張性 / 運用負荷>

## 候補案
- 案A: <概要>
- 案B: <概要>（必要なら案C）

## トレードオフ
- 案A: 利点 / 欠点
- 案B: 利点 / 欠点

## 推奨
- <どれを推すか＋理由（評価軸に紐づけて）>

## 未決事項 / 制約
- この段階では実装しない（設計提案のみ）
- <ユーザー確認が必要な前提>
```

## 品質チェック（生成後の自己点検）

- [ ] ゴールが検証可能か（「良くする」等の曖昧語になっていないか）
- [ ] 対象パスは推測でなく確認済みか（不確かなら「要確認」と明示したか）
- [ ] 受け入れ基準と検証手段が入っているか（その種別で必要なら）
- [ ] 不要なセクションで水増ししていないか
- [ ] 出力言語が入力に合っているか

## 良い例（バグ修正）

依頼: 「ログインのバリデーションがおかしい」→ 調査で対象を特定後、こう生成する。

```
## 目的
ログインフォームでメール未入力のまま送信するとクラッシュする問題を修正し、
未入力時はフィールド下にエラーメッセージを表示する。

## 症状 / 再現手順
1. /login を開く
2. メール欄を空のまま「ログイン」を押す
3. 期待: 「メールアドレスを入力してください」表示 / 実際: 画面が白くなる

## 対象
- src/features/auth/LoginForm.tsx（送信ハンドラの検証）

## 受け入れ基準
- [ ] 未入力送信でクラッシュしない
- [ ] 該当フィールドにエラーメッセージが出る
- [ ] このケースの再発防止テストを追加
- [ ] 既存の auth テストが緑

## 検証
- npm test src/features/auth
```
