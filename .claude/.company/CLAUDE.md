# storyline AI Company

## 基本ルール
- 常に日本語で応答する
- 結論ファースト。前置き・挨拶不要
- 確認より実行を優先。「こうします」と宣言してから動く
- 確認が必要: ユーザデータに触る操作・不可逆な操作・外部公開のみ
- 推測で書かない。不明点は明示 or 質問

## 組織
| 部署 | ディレクトリ | 責務 |
|------|-------------|------|
| 秘書 | secretary/ | 窓口・振り分け・進捗管理・ブリーフィング |
| 開発部 | dev/ | コード実装・レビュー・テスト |
| 企画部 | planning/ | 機能企画・仕様策定・スコープ判断 |
| デザイン部 | design/ | UI/UX 設計・デザイントークン・情報設計 |
| 広報部 | pr/ | README / 紹介文 / リリースノート / スクリーンショット |

AI 機能を持たないプロダクトのため **AI 部は置かない**。将来 AI 機能を入れるときは
`ai/` と対応する agent / skill を新設する。

## タスクフロー
1. 社長 → 秘書に指示
2. 秘書がタスク解釈 → 適切な部署に起票
3. 部署が実行 → 成果物を所定フォルダに保存
4. 部署間連携が必要 → 引き継ぎメモ付きで次の部署に起票
5. 秘書が完了確認 → TODO更新

## 部署間連携ルール

### 依頼の出し方
- 他部署への依頼は秘書経由が原則
- 緊急時は直接依頼可。ただし秘書に事後報告 (inbox/ にメモ)

### 引き継ぎメモ
- 部署をまたぐタスクは tasks/ 内のファイルに `## 引き継ぎ` セクションを追加
- 内容: 背景・やったこと・次の部署にやってほしいこと・注意点

### ブロッカー処理
- 他部署の完了待ちでブロックされたら秘書に報告
- 秘書はブリーフィングでブロッカーを可視化

### 定型連携パターン
- 新機能: 企画 → デザイン → 開発 → (公開するなら) 広報
- バグ修正: 秘書 → 開発 → 秘書
- 使い勝手の違和感: 秘書 → デザイン (診断) → 企画 or 開発
- データモデル変更を伴う機能: 企画 → 開発 (移行方針を先に確定) → デザイン

### レビュー依頼
- 開発 → デザイン部: UI 実装のデザインレビュー
- 企画 → デザイン部: 機能仕様の UX 観点レビュー
- デザイン → 開発部: 実装コスト・永続化への影響確認

## タスクファイル規約

`{部署}/tasks/` のチケットは以下に従う。`/status` `/briefing` `/done` `/retro` はこの形式を前提に読み書きする。

### 命名規則

- `YYYY-MM-DD-<slug>.md`（slug は kebab-case の英数字）。`YYYY-MM-DD` は起票日
- 発注書・連絡メモも同様

### 必須メタ行（チケット先頭・dash-bullet 形式）

```
- 作成日: YYYY-MM-DD        （または「- 起票日:」。起票日を表す）
- ステータス: **<語彙>**（任意の補足）
- 優先度: **<高|中|低>**     （省略時は「中」とみなす）
```

- **dash-bullet（`- `）+ 全角キー「ステータス」が必須**。英語キー `- status:`・YAML frontmatter
  `status:`・dash 無しの `ステータス:` はツールが検出できない
- 完了は `- ステータス: **完了**（YYYY-MM-DD 実施主体）` 形式を推奨（briefing の昨日完了判定が
  括弧内日付を読む）

### ステータス語彙（この 4 語のみ）

| 語彙 | 意味 |
| --- | --- |
| `未着手` | 起票済み・未着手 |
| `進行中` | 作業中・ブロック中も含む |
| `レビュー中` | 成果物のレビュー待ち |
| `完了` | クローズ |

- ツールは先頭語のみ検出する。ニュアンス（条件付き・GO 待ち等）は**全角括弧内に自由記述**で保全
  （例: `**進行中**（下書き完了・社長 GO 待ち）` / `**完了**（本稿・確定）`）
- 成果物側のライフサイクル語（ドラフト/本稿/確定 等）は tasks/ チケットでは使わない（下記参照）

## ディレクトリ構成と一次情報

| 種別 | ディレクトリ | 位置づけ |
| --- | --- | --- |
| **ワークチケット** | `{部署}/tasks/` | **ステータスの唯一の一次情報**。上記規約に従う。`/status` `/briefing` `/retro` はここだけを走査 |
| 成果物 | `planning/specs/` `planning/features/` `design/ui-specs/` `design/wireframes/` `design/style-guide/` `pr/content/` `pr/assets/` | 各チケットの納品物。ドキュメントライフサイクル語（ドラフト/レビュー/本稿/確定）を持つ。**status 走査対象外**。対応する tasks/ チケットへ相互リンクする |
| 連絡 | `planning/inbox/` `secretary/inbox/` | 部署間の未トリアージ連絡。秘書が処理。走査対象外 |
| 記録 | `dev/reviews/` `dev/qa/` `dev/tech-debt/` `secretary/decisions/` | レビュー指摘・QA・技術負債・社長決裁ログ |
| 生成物 | `secretary/todos/` `secretary/notes/` `secretary/plans/` | `/briefing` `/retro` が再生成する集計物。**手で status を二重管理しない**（一次情報は常に tasks/） |

### 運用ルール

- **完了タスクは `tasks/` に `完了` ステータスのまま残す**（`done/` 等へアーカイブ移動しない）。
  `/status` は完了を除外、`/briefing` `/retro` は日付で集計するため履歴を保ったまま自動で掃ける
- **成果物 ↔ チケットは相互リンク**（チケットに `- 本稿ファイル:` 等、成果物に `参照仕様:` 等）。
  ステータスはチケット側で管理し、成果物側のライフサイクル語と二重管理しない
- 空（`.gitkeep` のみ）の足場ディレクトリは各部署 agent / skill 定義が宣言する正規の出力先：
  `planning/features/`（機能候補）/ `planning/ux-research/`（UX 調査）/
  `design/wireframes/`（ワイヤーフレーム）/ `design/style-guide/`（デザイントークン）/
  `pr/analytics/`（反応記録）/ `secretary/notes/`（retro 出力先）/ `secretary/inbox/`（事後報告）。
  未使用でも参照元があるため削除しない

## プロダクト情報
- 名前: storyline
- 概要: シナリオの構成 (時系列) とキャラクターのつながりを整理するツール
- ターゲット: 個人の書き手 (小説 / 脚本 / シナリオ)。まずは作者自身が使う
- データ構造: 作品 > ストーリー > シークエンス > シーン + 作品直下にキャラクター
- スタック: Next.js 16.3 (App Router) / React 19.2 / TypeScript 5 / zustand 5 + immer /
  idb-keyval (IndexedDB) / dnd-kit / Tailwind v4
- サーバ: **無し**。API もデータベースも認証も課金も無い。データはブラウザの IndexedDB のみ
- バックアップ: ユーザが手動で書き出す `*.storyline.json` だけ
- テスト: **未導入** (方針は `.claude/docs/02-development-docs/09-test-strategy.md`)
- デプロイ: Vercel (サーバ側の状態を持たないので静的に近い形で載る)
