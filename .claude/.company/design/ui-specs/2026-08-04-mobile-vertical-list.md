## 1. 切り替えのブレークポイント

**決定: `md` (768px) 未満で縦リスト、768px 以上は既存カンバンのまま。**

- シークエンス列は `w-72`（288px 固定）+ `gap-3`（12px）。640〜767px では 2 列がぎりぎり
  収まるだけで余白が無くなり、列の端でのドラッグが指では狙いにくくなる。768px 以上
  （iPad 縦持ちなど）なら 2 列と 3 列目の頭が見え、一望性とドラッグ操作の両立が現実的
- ランドスケープの大型スマホ（例: 844px 幅）は 768px を超えるため引き続きカンバン。
  横向きは横スクロールでも構成を追いやすいので妥当な境界
- **実装方式**: JS の `matchMedia` によるツリー出し分けはしない。既存コードに
  `useMediaQuery` 相当のフックは存在せず（`sm:grid-cols-2` は CSS のみで解決している）、
  Tailwind の responsive utility で 2 つの DOM を **CSS 上だけ** 出し分ける
  （`hidden md:block` と `md:hidden` のペア）。SSR/CSR で判定が食い違うハイドレーション
  ミスマッチを避けられ、既存の実装方針とも揃う
- トレードオフ: 両方の DOM が常にマウントされる（非表示側も React ツリー上に存在する）。
  [08-performance-optimization.md](../../../docs/02-development-docs/08-performance-optimization.md)
  は「シーン数百件でも仮想スクロール不要」としており、この規模感なら許容範囲。体感が重いと
  分かった場合のみ、`useMediaQuery` 的なフック（SSR 時はカンバン相当を仮定）へ切り替える
  選択肢を残す

## 2. 縦リストの構造

**決定: シークエンス見出し（アコーディオン）+ 配下のシーン行。初期状態は全展開。**

```
[すべて折りたたむ / すべて開く]   ← トグルボタン
▾ シークエンス見出し 1  (n件) [▲][▼][✕]
  狙いのメモ（InlineText）
  シーン行 ×n
  [＋ シーンを追加]
▾ シークエンス見出し 2 ...
[＋ シークエンスを追加]
```

- **初期状態は全展開**。PC のカンバンは常に全シーンが見えている状態なので、縦リストへの
  切り替えでいきなり情報量が減る（畳まれて何も見えない）体験にしない。カンバンとの
  情報パリティを保つのが最優先
- 折りたたみ状態は**永続化しない**（画面のローカル state のみ、`Set<sequenceId>` 等）。
  ページを開き直すたびに全展開へ戻る。理由: IndexedDB 以外の永続化面（localStorage 等）を
  新設するとバックアップ対象外の状態が増え、ストレージまわりの検討事項が増える。
  UI 上のセッション内メモとして割り切る（`activeStoryId` や `openSceneId` と同じ
  「持たない」方針、[01-architecture-design.md](../../../docs/02-development-docs/01-architecture-design.md) §2）
- **一望性の担保策**: 縦リストは構造上、カンバンの「横に並べて一目で見渡す」ができない。
  代わりに以下の 2 段構えで代替する:
  1. 見出し行は折りたたんでも「タイトル + 件数」が残るため、**全シークエンスを畳めば
     目次のように全体像を一目で見られる**（＝縦方向でも「構成の一覧性」は確保できる）
  2. 画面上部の **「すべて折りたたむ / すべて開く」トグル**（`Button` `variant="ghost"`、
     ラベルは現在の状態に応じて反転）で、目次モードと詳細モードをワンタップで往復できる
- シークエンス見出しの操作要素:
  - 折りたたみ切替は**専用の chevron ボタン**（▾/▸）が担う。見出し行そのものを
    `role="button"` にはしない — 見出しには `InlineText`（`<input>`）が同居しており、
    `<button>` の中に `<input>` を入れるのは HTML 上不正（インタラクティブ要素の入れ子）。
    見出し行は素の `div`、chevron ボタン・`InlineText`・並べ替え/削除ボタンは
    **兄弟要素**として並べる
  - 折りたたみ中は `▲ / ▼ / ✕`（並べ替え・削除）を非表示にし、`chevron / タイトル / 件数`
    だけを残す。理由: 目次モードでの情報密度を上げる（「何を削るか」の実践）。展開すると
    「このシークエンスを触っている」状態とみなし、操作ボタン一式を出す
  - シークエンスの並べ替え（`▲ / ▼`）は [StoryTabs](../../../../src/components/StoryTabs.tsx)
    の「‹ / ›」ストーリー移動ボタンと同じ発想（境界で `disabled`）。
    `moveSequence(projectId, storyId, from, to)` をそのまま呼ぶだけで実装できる
    （ストア変更不要）
  - 削除ボタンは既存 [SequenceColumn](../../../../src/components/board/SequenceColumn.tsx) と
    同じ確認文言・挙動（`window.confirm` + `deleteSequence`）を流用する

## 3. 縦リストでのシーンカードの情報量

**決定: 既存 `SceneCardBody` はそのまま流用しない。同じデータ（`Scene` / `Character[]` /
`statusMeta`）を使う新規の横長 1 行コンポーネントを作る。**

- **考え方（スマホが基準）**: 出発点は「PC 版カードから何を削るか」ではなく、
  「スマホでシーンを一目で見分けるために最低限必要な情報は何か」で決める。
  そのうえで結果的に PC カードの情報の一部と重なる（サムネイル・番号・タイトル・時間/場所・
  ステータス）が、これは PC 側に合わせたのではなく、縦リストでも「同じシーンをどの画面でも
  同じ基準で識別できる」ことを優先した結果である
- 理由（レイアウト面）: `SceneCardBody`
  （[SceneCard.tsx](../../../../src/components/board/SceneCard.tsx)）は 288px 幅の列を前提に、
  サムネイル全幅 + タイトル + メタ + `line-clamp-3` の要約 + キャラチップ（名前付き）+
  ステータスバッジを縦積みする構造。375px 幅でそのまま 1 カラム化すると 1 行（1 シーン）が
  非常に高くなり、スクロール量が増えて縦リストの一望性がむしろ悪化する
- 表示する情報（削るもの / 残すもの）:

  | 項目 | カンバン (`SceneCardBody`) | 縦リスト行 | 判断 |
  | --- | --- | --- | --- |
  | サムネイル | 全幅 `aspect-video` | 左端の固定正方形（目安 64×64）。無ければ何も出さない領域を空けず、行の高さは他要素で決まる | 縮小して残す（視覚的な見分けやすさは一覧性に効く） |
  | シーン番号 (S12) | あり | あり | そのまま残す |
  | タイトル | あり (1〜2行) | あり (1行 truncate) | 主情報なので残す |
  | 時間 / 場所 | あり (1行) | あり (1行 truncate、時間・場所とも空なら行ごと出さない) | 残す |
  | あらすじ | `line-clamp-3` | **削る** | 高さの最大要因。タップして開けば読める |
  | 登場キャラクター | 色ドット + 名前チップ (最大4+N) | **簡略化**: 色ドットではなく `名前, 名前 +N` のテキストのみ | 色チップ運用は残すとレイアウトが崩れやすく、a11y 的にも「色だけに頼る」誤解を生みやすい。名前テキストなら常に文字で状態が伝わる。詳細（役割等）はタップで開くドロワーで確認 |
  | ステータス | ラベル付きバッジ | ラベル付きバッジ（同じ `SCENE_STATUSES[].className` を使用） | 色だけに頼らない a11y 要件を維持したまま残す |

- レイアウト（詳細は [ワイヤーフレーム](../wireframes/2026-08-04-mobile-vertical-list.md) 参照）:
  行は `role="button"` の入れ子を避けるため **plain `div`** を親にし、
  「サムネイル + テキスト2行 + ステータス」をまとめた **1 個の `<button>`**（タップでシーン編集
  ドロワーを開く。既存カードの `onClick` と同じ役割）と、並べ替え用の `▲ / ▼` の
  **兄弟 `IconButton`** で構成する（入れ子にしない。2 節の理由と同じ）
- コンポーネント名・配置は開発部の裁量とするが、`SceneCardBody` と同じ関心事
  （`characterIds` からのキャスト解決、`statusMeta()`）を再利用しつつ JSX は別物になるため、
  `src/components/board/` 配下に新規ファイルを置く形を想定（例:
  `MobileSceneRow.tsx` / `MobileSequenceList.tsx`。命名は実装側判断）

## 4. 並べ替えの操作

**決定: ドラッグは実装しない。上下移動ボタン（▲ / ▼、44×44）方式にする（シーン・シークエンス共通）。**

- 理由:
  - 縦リストは並べ替えジェスチャ（上下ドラッグ）とスクロールジェスチャが**同一軸**になる。
    kanban の `PointerSensor` + `activationConstraint: { distance: 6 }`
    （[07-drag-and-drop.md](../../../docs/02-development-docs/07-drag-and-drop.md) §1）は
    横方向の列内で距離のみで判定しているが、縦一列では距離だけでは「持ち上げたい」か
    「スクロールしたい」かを区別できない。dnd-kit で区別するには長押し猶予
    （`delay` + `tolerance`）が定石だが、「持ち上げるまでの間、意図せずスクロールしてしまう」
    体験になりやすく、検証コストが高い
  - D&D は「storyline で最も壊れやすい箇所」と明記されている
    （同ドキュメント冒頭）。数百規模のシーンを想定するモバイルでリスクを追加で取るより、
    確実に動く手段を優先する
  - 上下移動ボタンは **[StoryTabs](../../../../src/components/StoryTabs.tsx) の
    「‹ / ›」ストーリー移動ボタンと同じパターンの流用**であり、実装コストが低い
    （境界で `disabled`、`disabled:opacity-30` の見た目もそのまま流用できる）
  - スクリーンリーダー・キーボード操作にも強い（ドラッグは実質タッチ/マウス専用だが、
    ボタンは `Tab` + `Enter` で誰でも操作できる）
- **PC のカンバン（`md` 以上）はドラッグ D&D のまま変更しない**。今回の決定はあくまで
  `md` 未満の縦リストのみに適用する
- シーンの ▲ / ▼ は**同一シークエンス内のみ**で完結させる（先頭シーンの ▲、末尾シーンの ▼は
  `disabled`）。シークエンスを跨ぐ移動は境界を越える動きに割り当てない
  （「上下移動」の意味が「前後のシークエンスへ越境」にすり替わると直感的でなくなるため）。
  跨ぎ移動は決定 5 のシーン編集ドロワー側に一本化する
- 実装は `moveScene(projectId, storyId, sceneId, sequenceId, index - 1 | index + 1)` /
  `moveSequence(projectId, storyId, from, from - 1 | from + 1)` の呼び出しのみ。
  **ストア API の追加変更は不要**
- 将来モバイルでのタッチドラッグを再検討する余地は残すが、別チケットとする
  （本チケットのスコープ外）

## 5. シークエンス跨ぎの移動

**決定: シーン編集ドロワー ([SceneEditor](../../../../src/components/SceneEditor.tsx)) に
「所属シークエンス」の選択項目を追加する。移動は常に移動先の末尾に追加。**

- 理由:
  - 縦リストの行に「移動」ボタンをもう1つ足すと、44px 幅の ▲/▼ に加えてさらに専用の
    タップ領域が要り、行が窮屈になる（誤タップのリスクも増える）
  - シーンをタップすると既にシーン編集ドロワーが開く導線がある。そこに移動先を選ぶ項目を
    足せば、**別の画面やモーダルを増やさずに**「編集の流れを止めない」まま移動できる
    （[01-architecture-design.md](../../../docs/02-development-docs/01-architecture-design.md) §4
    の「画面遷移は 2 つだけ」原則にも沿う）
  - このフィールドは**ブレークポイントに関わらず常時表示**する（分岐を増やさずシンプルに保つ）。
    デスクトップでもマウスでドラッグせずに列を跨げる副次的な利点がある
- 移動は常に**移動先シークエンスの末尾**に追加する（位置の細かい指定は求めない）。
  移動後に必要なら決定 4 の ▲/▼ で微調整すればよく、「切り取り→末尾に貼る→ボタンで微調整」
  の組み合わせで実質どの位置にも動かせる。実装は
  `moveScene(projectId, storyId, sceneId, 選んだ sequenceId, 十分大きい index)` の 1 回で済む
  （現状 [Board.tsx](../../../../src/components/board/Board.tsx) の `APPEND` 番兵と同じ考え方。
  `moveScene` 側で `Math.min(toIndex, target.scenes.length)` に丸められるため、
  `Number.MAX_SAFE_INTEGER` を渡すだけでよい）
- 選択肢から**現在のシークエンスは除外**する（無意味な自己移動を選べないようにする）
- **ストーリー内のシークエンスが 1 つしか無い場合はこのフィールド自体を非表示にする**
  （移動先が無いため。[CharacterPanel](../../../../src/components/CharacterPanel.tsx) が
  キャラクター0件のときにヒント文だけ出す、既存の「無いものは出さない」流儀に合わせる）
- **実装メモ（デザイン部としての注意喚起。最終判断は開発部）**:
  - `SceneEditor` は現状 `characters` しか受け取っておらず、`story`（または
    `sequences` と現在の `sequenceId`）を新しく props で渡す必要がある。呼び出し元
    ([projects/[projectId]/page.tsx](../../../../src/app/projects/[projectId]/page.tsx)) の
    変更を伴う。ストアの型やデータ構造は変えない
  - フォーム部品として `<select>` が要るが、[ui.tsx](../../../../src/components/ui.tsx) には
    まだ `Select` 相当が無い。`TextInput` / `TextArea` と同じ `INPUT_CLASS` を使う `Select`
    プリミティブの新設を推奨する（「足りないものは ui.tsx に追加する」原則
    [06-ui-design.md](../../../docs/02-development-docs/06-ui-design.md) §2）。ただし
    `INPUT_CLASS` の `py-2` だけでは高さが 44px に届かないため、この用途では
    `min-h-11`（44px）を明示的に足すこと（決定 8 のタップ領域表に記載）

## 6. ストーリータブ・ヘッダ・各パネルの縦画面での収まり

**決定: 構造は変更不要（既に 375px 幅で崩れない）。ただし共有プリミティブのタップ領域には
既知のギャップがあり、今回新設する要素だけは仕様として 44px を満たす。既存プリミティブの
底上げは別途スコープ確認する。**

- **ヘッダ**（[page.tsx](../../../../src/app/projects/[projectId]/page.tsx) 冒頭）: 既に
  `flex flex-wrap items-center gap-3` で、幅が足りなければボタンが折り返す構成になっている。
  375px 幅でも横スクロールは発生しない。**構造変更は不要**
- **ストーリータブ**（[StoryTabs.tsx](../../../../src/components/StoryTabs.tsx)）: 既に
  `overflow-x-auto` + `.thin-scroll` で横スクロールが**タブの中に閉じている**（body に漏れない）。
  **構造変更は不要**
- **ドロワー**（`Drawer`、[ui.tsx](../../../../src/components/ui.tsx)）: `w-full max-w-md`
  なので 375px 幅では実質フルスクリーン表示になる。**構造変更は不要**
- **片手操作（画面下部への操作の集約）の検討**: 縦リストで最も頻度が高い操作は
  「シーンをタップして開く」「▲/▼ で並べ替える」で、これらは**スクロール位置＝今見ている
  場所にそのまま存在する**ため、追加の配慮をしなくても常に指の届く位置に来る。
  相対的に頻度が低い操作（シークエンス追加・全体の折りたたみ切替）は、リストの末尾／先頭に
  固定で置く現状のままとし、**フローティングアクションボタン (FAB) のような画面下部固定 UI は
  新設しない**。理由: 本アプリに FAB 相当のパターンが無く、`Modal` / `Drawer` の出入りも
  控えめなモーションに留める方針（[06-ui-design.md](../../../docs/02-development-docs/06-ui-design.md) §6）
  と合わせ、新しい UI 言語を追加するコストの方が「シークエンス追加のために一度スクロールする」
  程度の手間より大きいと判断した。ヘッダの操作（キャラクター管理・書き出し）も同様に低頻度
  なので、画面上部のままで問題ない
- **既知のギャップ（今回のスコープ外だが明記）**: `Button`（`px-3 py-1.5` ≈ 32px 高）・
  `IconButton`（`h-7 w-7` = 28px）は、いずれもタップ領域 44×44px の目安に届いていない。
  これは新規に作る要素ではなく [ui.tsx](../../../../src/components/ui.tsx) の
  **既存プリミティブ**なので、ヘッダの「キャラクター」「書き出す」ボタン、ドロワーの
  フッターボタン、ストーリータブの「‹ / › / ✕」など、縦リストと無関係な既存箇所にも
  横断的に影響する。本チケットの範囲でこれを底上げすると影響範囲がカンバン列の
  ドラッグハンドルなど他画面にも及ぶため、**このチケットでは対応しない**。
  別チケット化するかは社長・開発部に確認する（決定 10「実装側で判断が要る点」参照）
- 上記を踏まえ、**今回新設する縦リスト固有の要素は個別に 44×44px を満たす**設計にしている
  （決定 8 の表）。既存プリミティブへの依存を避けたい箇所（見出しの chevron・シーン行の ▲/▼・
  すべて折りたたむトグル）は、`IconButton` / `Button` を使う場合でも `className` で
  `h-11 w-11` 等を明示し、サイズを保証すること

## 7. PC とスマホが競合したときの優先順位

**決定: 表現・挙動が PC カンバンと縦リストで競合した場合、常にスマホ（縦リスト）を優先する。**

- 背景: [決裁記録](../../../secretary/decisions/2026-08-04-accounts-and-server-decisions.md)
  差分1により、利用想定が「スマホ対応」から「スマホがメイン」に格上げされた。設計の起点も
  「PC 基準・スマホはフォールバック」から反転している
- 本仕様内での適用例:
  - 決定 3 の情報量は「PC から何を削るか」ではなく「スマホで何が要るか」を起点に決めている
  - 決定 5 の「所属シークエンス」フィールドはスマホ側の必要性から生まれたものだが、
    実装を分岐させずスマホ・PC 双方の `SceneEditor` に常時出す（スマホの解决策をそのまま
    PC にも適用する＝スマホ優先の一形態）
  - 今後、両画面で同じ操作に別の答えが必要になった場合（例: 将来カード情報を増減する提案が
    出た場合）は、**まずスマホでの一望性・タップ操作性を基準に判断し、PC 側はその結果を
    広い画面向けに展開できるか」を後から検討する**順序で判断する

## 8. タップ領域 (44×44px) の明記

WCAG 2.5.5 相当。今回新設する対話要素はすべて以下を満たすこと。

| 要素 | 最小サイズ | 備考 |
| --- | --- | --- |
| シークエンス見出しの折りたたみ chevron | 44×44 | `IconButton` 流用時は `className="h-11 w-11"` 等で明示的に上書き |
| シークエンス ▲ / ▼（並べ替え） | 各 44×44 | 展開時のみ表示。境界で `disabled` |
| シークエンス ✕（削除） | 44×44 | 展開時のみ表示。確認ダイアログは既存文言を流用 |
| シーン行の「開く」ボタン（サムネイル+テキスト+ステータス） | 幅いっぱい ×44 以上 | サムネイル (64px) がある分、自然に 44px を超える |
| シーン行の ▲ / ▼（並べ替え） | 各 44×44 | 縦に 2 個並べて右端に配置（詳細はワイヤーフレーム） |
| すべて折りたたむ / 開くトグル | 44 以上（高さ） | `Button variant="ghost"` をベースに高さのみ明示的に確保 |
| 「＋ シーンを追加」「＋ シークエンスを追加」 | 44 以上（高さ） | 既存 `Button` は高さ不足のため、この 2 箇所は縦リスト用に高さを明示する（横幅いっぱいのボタンなので視覚的な違和感は出ない） |
| シーン編集ドロワー内「所属シークエンス」の `<select>` | 44 以上（高さ） | `INPUT_CLASS` だけでは不足。`min-h-11` を明示 |

Tailwind の `h-11` / `w-11` はいずれも 44px（`2.75rem`）で、既存のスペーシングスケールの
範囲内（新しい中間値を発明しない）。

## 9. デザイントークン確認

本仕様で新しく使う色は無い。すべて既存のセマンティックトークンで表現できることを確認済み:

- 面: `bg-surface`（見出し・行の背景）/ `bg-surface2`（一段沈んだ背景、折りたたみ時のホバー等）
- 境界線: `border-line`
- 文字: `text-fg`（本文）/ `text-muted`（メタ情報・登場人物テキスト・件数）
- アクセント: `bg-accent` / `text-accentfg`（選択中の強調、必要なら）
- 破壊的操作: `text-danger`（削除ボタン。既存 `IconButton className="hover:text-danger"` を流用）
- 例外（データとしての色、既存のまま追加無し）:
  - ステータスバッジ: `SCENE_STATUSES[].className`（[types.ts](../../../../src/lib/types.ts)）を
    そのまま使う。新しいバッジ色は増やさない
  - キャラクター識別色: 今回の縦リスト行では**使わない**（決定 3 で色ドットをやめてテキスト
    表記にしたため）。`CHARACTER_COLORS` は既存の用途（チップ・相関図）のまま変更無し

**生の色ユーティリティ（`text-gray-500` 等）は増やさない。**

## 10. 実装側で判断が要る点 / 社長に確認したい点

1. **既存 `Button` / `IconButton` のタップ領域不足（28〜32px）を、この機に底上げするか**。
   底上げする場合はヘッダ・ストーリータブ・両ドロワーのフッターなど、縦リスト以外の
   既存 UI にも影響する（デスクトップの見た目にも波及しうる）。本仕様では**このチケットの
   範囲外**として扱ったが、モバイルがメイン想定に格上げされた
   （[決裁記録](../../../secretary/decisions/2026-08-04-accounts-and-server-decisions.md) 差分1）
   ことを踏まえると、近い将来どのみち対応が要る可能性が高い。別チケットとして起票するか
   このチケットに含めるか、社長判断を仰ぎたい
2. **`IconButton` の `className` でのサイズ上書きは Tailwind のユーティリティ生成順に
   依存し、確実に上書きできる保証が無い**（`h-7 w-7` がベースクラスに固定されているため）。
   実装時は `className` 上書きに頼るより、`IconButton` に `size` prop
   （例: `size="touch"` → `h-11 w-11`）を追加する形を推奨するが、これは開発部の実装判断
3. 「すべて折りたたむ / 開く」の折りたたみ状態を**永続化しない**方針にしたが、シーン数が
   非常に多い作品では毎回全展開から始まるのが煩わしい可能性がある。実際に使ってみて
   要望が出たら、`localStorage` 等の追加を検討する（今回は見送り）
