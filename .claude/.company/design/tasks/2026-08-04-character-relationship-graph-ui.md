## 概要

確定した spec を、**画面上でノードを配置し、ノード同士をドラッグで結線できる** UI 仕様に落とす。
storyline に「キャンバス上で直接編集する画面」は存在せず、既存の
[ui.tsx](../../../../src/components/ui.tsx) のプリミティブだけでは足りない可能性が高い。
**何が足りないかを最小限で洗い出す**のがこのチケットの実質的な価値。

## 設計する範囲

1. **相関図キャンバスそのもの** — ノード（キャラクター）の見た目、グループ枠とラベル、
   ラベル付き有向エッジ
2. **編集操作** — ノードの配置（移動）、**ノード同士をドラッグで結ぶ**操作、エッジの選択・
   ラベル編集・削除、グループ枠の作成と割り当て
3. **ビューポート操作** — 参照ビジュアルにある全画面 / コピー / パン十字 / リセット / ズーム。
   **どれを採り、どれを採らないかを理由つきで**（そのまま全部移植する必要はない）
4. **画面内での置き場所** — spec が決めた配置（ドロワー / タブ / 専用ルート）に合わせた導線
5. **スマホ幅 375px での成立のさせ方** — 本プロダクトは**モバイルファースト**。
   PC とスマホで仕様が競合したらスマホを優先する

### 決め打ちしないこと（重要）

- **実装方式（React Flow か、既存 dnd-kit + 自前 SVG か）を UI 仕様で固定しない**
  （秘書決裁 D-6）。社長は方式を dev / design に委任したが、**方式の結論は dev の移行方針
  チケットに置く**。design は「この操作感が要る」という**要件リスト**を出し、dev がそれを
  満たせるかで方式を選ぶ。仕様側でライブラリ名を前提にした表現を使わないこと。

## 引き継ぎ

### 企画部 → デザイン部（2026-08-04・spec 確定）

**① 背景**

社長依頼「相関図を GUI で作れるようにする」の仕様が確定し、**このチケットのゲートは開いた**。
storyline は「キャラクターのつながりを整理するツール」を名乗りながら、つながりを表す手段が
`Scene.characterIds`（＝同じシーンに出た）しか無く、「兄妹」「裏切る」のような
**シーンに現れない関係**を書く場所が無かった。そこを 1 枚の図で埋める。

**② 成果物パス**

- [planning/specs/2026-08-04-character-relationship-graph-spec.md](../../planning/specs/2026-08-04-character-relationship-graph-spec.md)（本稿・確定）

**③ デザイン部の具体アクション（spec のどこが直接効くか）**

| spec の節 | design が受け取る決定 |
| --- | --- |
| 1（エッジの属性） | エッジが持つのは**ラベル（自由テキスト）と向き 3 値だけ**。線種・色・強度は**持たない**ので、**凡例を設計しなくてよい**。双方向は 2 本ではなく 1 本 + 属性で描く |
| 5（配置場所） | **作品画面のメイン領域を「構成 ↔ 相関図」で切り替える**。新ルートもドロワーも使わない。切替はストーリータブより上位に置き、相関図表示中はストーリータブを隠す。**キャラ本体の編集（名前 / 立ち位置 / メモ / 色）は既存 `CharacterPanel` に一本化**し、相関図側に同じ入力欄を作らない |
| 7（グループ枠） | **単層・1 キャラ最大 1 グループ**。枠の位置と大きさは**メンバーの外接矩形から自動算出**（データとして持たない）。枠が持つのは名前だけ。空グループの図上の扱いは design 判断 |
| 8（375px） | **最大の緊張点。ここが本チケットの山**。閲覧も編集も可だが、**ドラッグ結線をスマホの必須経路にしない**（タップ 2 段階を必ず用意）。375px は「全体表示＝構造を見る（文字は読めなくてよい）」「フォーカス表示＝1 人の直接のつながりだけを読む」の**2 段構え**で成立させる。ワンタップで往復できること。**関係リストは v1 に含む**（細い線をタップさせないため） |
| 9（ノードの中身） | ノードは「**名前 ＋ 立ち位置（`role`）＋ 識別色**」の 2 行。`note` は出さない。画像は持たない。**全キャラクターが必ずノードになる**（非表示フラグは無い） |
| 2（座標） | ノードのドラッグ移動は 375px でも行う。**縦リストでドラッグを捨てた理由（並べ替え軸とスクロール軸の衝突）はここには当てはまらない**（掴む対象で区別できる）。ただし**ノードのドラッグとキャンバスのパンの取り違え**が新しい緊張点。「リセット (⟳)」は初期表示に戻すだけで、**ノードの配置は戻さない** |
| 14（スコープ） | 「作らないもの」の一覧が判断の一次情報。**画像コピー / 印刷 / 複数選択 / 整列 / Undo / 自動レイアウトは v1 では作らない** |

**④ 決定待ち**

- 社長の Q1〜Q6（spec 17 章）。**すべて既定があるので待たずに着手してよい**。
  design に効くのは主に **Q1（キャラクター数の規模）**と **Q4（スマホの主用途）**。
  既定は「30 人前後で構造が読めることを目標」「見る / 作るの両方できる形」。
- **実装方式は決めない**（社長が dev / design に委任し、結論は dev の移行方針チケットに置く）。
  design は **UI 要件リスト**を出すこと。

**⑤ 次フェーズへの開放質問（spec 16 章「未確認」より design が担当するもの）**

1. 375px でノードのドラッグとキャンバスのパンを取り違えずに操作できるか（実機確認）
2. 375px の全体表示で 20〜30 人規模の図が「構造として読める」か
3. ノード内テキスト / エッジラベルが、識別色を背景に使った場合でもダーク / ライト両方で
   コントラスト比 4.5:1 を満たせるか
4. 既存プリミティブ（`Drawer` / `Modal` / `Button` / `IconButton` / `InlineText`）で
   相関図の周辺 UI が足りるか。足りないものだけを列挙する
