## 概要

現在のボードは幅 288px の列を横スクロールする前提で、スマホの縦画面だと 1 列強しか見えない。
社長決裁で「狭い画面では縦リストに切り替える」と確定したので、その UI 仕様を固める。
サーバ移行を待たずに単独で出せるため、スマホ利用を最速で成立させる担当になる。

**2026-08-04 の前提変更（重要）**: 社長の利用想定が「**スマホがメイン**」に更新された。
縦リストは「小さい画面向けの劣化版」ではなく**基準となる表示**として設計する。
PC のカンバンは、その基準を広い画面に展開したものと位置づける。
**PC とスマホで仕様が競合したらスマホを優先する**（決裁記録の追記・差分1）。

## 決めること

1. 切り替えのブレークポイント（`md` 未満で縦リスト、で良いか）
2. 縦リストの構造（シークエンス見出し + 配下のシーン。折りたたみの初期状態はどちらか）
3. 縦リストでのシーンカードの情報量（サムネイル・キャラチップ・ステータスをどこまで出すか。
   PC 版と同じ [SceneCard](../../../../src/components/board/SceneCard.tsx) を流用できるか）
   — **スマホが基準**なので「PC 版から何を削るか」ではなく「スマホで何が必要か」から決める
4. 並べ替えの操作（ドラッグを維持するか、上下移動ボタンにするか。指での長押し判定と
   スクロールの取り合いをどう避けるか）
5. シークエンス跨ぎの移動をスマホでどう提供するか（ドラッグが厳しいなら「移動先を選ぶ」UI）
6. ストーリータブ・ヘッダ・各パネル（[Drawer](../../../../src/components/ui.tsx)）の縦画面での収まり
   — 片手操作を想定し、主要操作が画面下部に届く配置か検討する
7. **【追加】PC とスマホで表現が競合したときの優先順位を仕様に明記する**
   （dev が実装中に迷わないようにするため。「スマホ優先」の一文で足りる）

## 結果サマリ（7点の決定）

1. **ブレークポイント**: `md`（768px）未満で縦リスト、以上は既存カンバンのまま。
   実装は CSS の responsive utility（`hidden md:block` / `md:hidden`）による DOM 出し分け。
   JS の `matchMedia` は使わない（ハイドレーションミスマッチ回避、既存方針と整合）
2. **縦リストの構造**: シークエンス見出し（アコーディオン、専用 chevron ボタンで開閉。
   見出し行を丸ごと `role="button"` にはしない — `InlineText` の `<input>` を
   `<button>` に入れられないため）+ 配下のシーン行。初期状態は**全展開**
   （カンバンとの情報パリティ優先）。「すべて折りたたむ / 開く」トグルで目次モードとの
   往復を用意し、一望性を代替する（折りたたみ時は「タイトル + 件数 + ステータス内訳の
   テキスト集計」だけの目次表示になる）。折りたたみ状態は永続化しない（ローカル state のみ）
3. **シーンカードの情報量**: `SceneCardBody` は流用せず新規の横長 1 行コンポーネントを作る。
   サムネイル(64×64・無くても枠は確保)・番号・タイトル・時間/場所・ステータスは残し、
   あらすじは削る。**登場キャラクターは PC と同じ「色ドット + 名前」を維持する**
   （テキストのみへの簡略化はしない。識別色はキャラクターのつながりを一望する核心情報の
   ため。幅の制約は最大表示件数の削減 4→3 件 + 折り返し禁止で吸収する）。
   行は「開く用の `<button>`」と「▲/▼ の `IconButton`」を**兄弟**として構成し、
   ボタンの入れ子を避ける
4. **並べ替え操作**: ドラッグは実装せず、上下移動ボタン（▲/▼、44×44、StoryTabs の
   ‹/› と同じ disabled パターンを流用）。理由は (a) 縦一列だと並べ替えとスクロールの
   ジェスチャが同一軸で衝突する (b) D&D は本コードベースで最も壊れやすい箇所
   (c) ボタンならキーボード/スクリーンリーダーでも操作できる。シーンの上下移動は
   同一シークエンス内のみ（境界を越えない）
5. **シークエンス跨ぎの移動**: シーン編集ドロワーに「所属シークエンス」選択を追加し、
   選ぶと移動先の末尾に即移動（`moveScene` の `toIndex` に大きな値を渡すだけ）。
   ブレークポイントに関わらず常時表示（PC にも同じ導線を出す＝分岐を増やさない）。
   現在のシークエンスは選択肢から除外、シークエンスが1つの作品ではフィールド自体を隠す
6. **ヘッダ・タブ・ドロワーの収まり**: 配置の構造は既存のまま 375px で崩れないため変更不要。
   ただしタップ領域は `md` 未満で**新規要素・既存プリミティブを問わず**すべて 44×44px に
   拡張する（ヘッダの「キャラクター」「書き出す」、ストーリータブの「‹/›/✕」、両ドロワーの
   フッターボタンも対象。`md` 以上は現状サイズを維持し PC の情報密度を崩さない）。
   フローティングアクションボタン等の新規 UI パターンは見送り（頻出操作はスクロール位置に
   そのまま存在するため片手操作の妨げにならない、かつ新しい UI 言語を増やすコストが
   見合わないと判断）
7. **PC/スマホ競合時の優先順位**: 常にスマホ優先。仕様書冒頭と専用の章に明文化
   （情報量・タップ領域は競合時にスマホ側を優先し PC を無理に合わせない。決定5のように
   スマホ発の解決策を分岐させず PC にもそのまま展開する場合もある）

詳細な理由づけ・ワイヤーフレームは本稿ファイルを参照。

- 注意点（特にタッチ DnD の方式選択の理由）:
  - **長押しドラッグを選ばなかった理由**: (a) タッチでの起動判定は「距離」でなく
    「長押し(delay)」が要り、押した瞬間に動く PC 体験と乖離する (b) 縦リストは
    **ページ全体がスクロールコンテナ**なので、画面外のシークエンスへドラッグで運ぶには
    自動スクロール実装が要り、実装・検証コストが跳ね上がる
    （[07-drag-and-drop.md](../../../docs/02-development-docs/07-drag-and-drop.md) が
    「最も壊れやすい箇所」と明記している既存のドラッグ実装に、自動テスト無しでタッチ分岐を
    足すことになる） (c) スマホが主戦場になった以上、並べ替えの不具合の影響ユーザ数が
    最大になるため信頼性を優先した (d) 44×44 のタップ領域要件・スクリーンリーダー操作の
    いずれもボタン方式の方が素直に満たせる（dnd-kit のドラッグ a11y 対応 =
    `KeyboardSensor` は現状未実装）
  - ボタン方式・跨ぎ移動ともに既存の `store.moveScene` / `store.moveSequence` をそのまま
    呼べる設計にした。**`src/lib/` への変更は不要**
  - PC 側のドラッグ実装（`Board.tsx` / `SequenceColumn.tsx` / `SceneCard.tsx`）は
    **変更しない**。モバイル用の並べ替え UI は新規コンポーネントとして追加する
  - `ui.tsx` の `Button` / `IconButton` は現状タップ領域が 44×44 未満（`IconButton` は
    `h-7 w-7` = 28px）。`md` 未満でのみ 44px 相当へ拡張し、`md` 以上は現状サイズを保つ
    レスポンシブ上書きを推奨した（`size` prop の新設が本命だが実装方法は dev の判断）
  - 折りたたみ状態・シークエンス跨ぎ移動の「所属シークエンス」いずれもデータモデル変更なし
    （前者はローカル `useState`、後者は既存 `Scene.` フィールドの参照先を変えるだけ）
  - 実装後はデザイン部にレビューを依頼すること（`npm run dev` を Claude 側で起動しない
    運用のため、スクリーンショットまたは実機確認結果の共有を推奨）
