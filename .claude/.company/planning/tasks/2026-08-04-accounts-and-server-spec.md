## 概要

スマホからの利用と複数人での利用のため、ブラウザ完結をやめてアカウント制に移行する。
方式は社長決裁で確定済み（Google ログイン / 作品は本人のみ / Neon+Prisma / Blob）なので、
このチケットは **移行に伴って決まっていない仕様の穴を塞ぐ** ことが目的。後続の dev 実装が
判断に迷わない状態を作る。

**2026-08-04 の追加指示で前提が 2 点変わった**（詳細は決裁記録の「追記」節）。
スマホは「対応する画面のひとつ」ではなく**メイン想定**になり、JSON 書き出しの位置づけが
一時再保留になった。この 2 点が下記「決めること」の 7〜9 に相当する。

## 決めること

1. ログイン前に見せる画面（ランディングを作るか、いきなり Google ボタンだけか）
2. 未ログイン時のルーティング（`/` を保護するか、`/login` へ飛ばすか）
3. 既存ローカルデータを持つユーザの導線（初回ログイン後に「JSON を読み込む」を促すか）
   — **移行手段は JSON 経由で確定（決定 7 = (b)・社長確定済み）**。決めるのは促し方と画面
4. ローカル版の扱い（決裁では「廃止」。移行猶予期間を設けるか、いつ IndexedDB 読み出しを消すか）
5. 作品数・シーン数・画像サイズの上限（Neon / Blob の無料枠を守れる値）
   — スマホのカメラロール画像が入る前提で見積もること
6. 退会・データ削除の要否（個人利用なので最小で良いか）
7. **【追加】JSON 書き出し／読み込みの存廃** → **(b) で社長確定済み（回答日 2026-08-04）**
   - 確定内容: 「DB が正本になるのでバックアップの主手段としては廃止するが、
     既存 IndexedDB データをサーバへ持ち込む**移行経路としては残す**」
   - 本 spec では (b) を**所与の前提**として、「書き出し UI をいつ落とすか」
     「移行経路としての JSON をどの画面で使うか」を具体化する（存廃の再検討はしない）
   - 制約: 移行完了前に書き出しを消さないこと（既存作品を DB へ持ち込む手段が失われるため）
8. **【追加】モバイルファーストの適用範囲と判断基準**
   - PC とスマホで仕様が競合したときは**スマホを優先する**（決裁で確定）。これを spec に明文化し、
     design / dev が個別に迷わないようにする
   - サーバ移行後に増える画面（ログイン / 作品一覧 / エラー）もスマホ幅 375px を基準にする旨
9. **【追加】オフライン利用を「保留のまま」にする理由を 1 行残す**
   - スマホがメインなら電波の無い場所で使われる可能性が上がるため、
     「なぜ今回のスコープに入れないか」を書いておかないと後で蒸し返される
