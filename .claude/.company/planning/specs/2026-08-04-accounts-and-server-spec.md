### 0-3. データモデルが増えることのコストとリスク（企画部の必須併記）

この移行は「項目を 1 つ足す」類ではなく、**保存先そのものを差し替える**。

| 増えるもの | 移行コスト | データ消失リスク |
| --- | --- | --- |
| `User` / Auth.js の `Account`・`Session` | 新規。既存データとの対応は無い | 低（作り直せる） |
| `Project` / `Story` / `Sequence` / `Scene` / `Character` ＋ シーン⇔キャラの中間表 | 既存 `Project` 型の全フィールドを写す。対応表を dev が作る（移行方針チケットの完了条件） | **高**。写し漏れた項目は、JSON を取り込んだ瞬間に静かに消える |
| **並び順の列**（現行は配列の添字で `order` を持たない） | DB では明示的な順序が要る。ローカル版の設計原則（[01-storyline-concept.md](../../../docs/01-project-overview/01-storyline-concept.md)）とのズレを dev が吸収する | **高**。並び順＝時系列そのものなので、崩れると作品の意味が壊れる |
| `Scene.thumbnail` の意味変更（data URL → Blob の URL） | 取り込み時に data URL を Blob へ移す | 中。変換に失敗した画像は復元できない |

- **実日付を持たない設計は移行後も変えない**。`createdAt` / `updatedAt` 以外の日付列を足さない。
- 移行が成功したと言える条件は [5](#5-既存ローカルデータを持つユーザの導線チケット-3) の「受け入れ条件」で定義する。

## 1. 貫く原則: モバイルファースト（チケット 8）

> **PC とスマホで仕様が競合したら、スマホを優先する。**

- **なぜ**: 社長の追加指示でメイン利用形態がスマホに確定した（決裁記録 差分 1）。
  縦リストは「小さい画面向けの劣化版」ではなく**基準となる表示**になる。
- **基準幅は 375px**（iPhone SE / mini 相当）。この移行で増える画面（`/login`・
  アカウントメニュー・エラー・404）も 375px で成立してから PC 幅へ広げる。
- **具体的な適用のしかた**（design / dev が個別に迷わないための運用ルール）:

| 場面 | 判断 |
| --- | --- |
| ヘッダに置くボタンが多くて 375px に収まらない | **ボタンを減らす**。PC だけ表示する分岐を増やさない |
| PC で便利だがスマホで邪魔な要素 | 落とす。「PC のみ表示」は最後の手段 |
| ポインタ前提の操作（hover で出る、右クリック、細かいドラッグ） | タップだけで完結する代替を必ず用意する |
| 情報密度 | スマホで読める密度を基準にし、PC では余白と列数で広げる |

- ボード（カンバン ↔ 縦リスト）の具体的な UI は
  [design/tasks/2026-08-04-mobile-vertical-list-ui.md](../../design/tasks/2026-08-04-mobile-vertical-list-ui.md) の管轄。
  本稿はサーバ移行で**新しく増える画面**に対して同じ原則を適用することを宣言するに留める。
- タップ領域サイズなどの具体値はデザイン部の仕様に従う（本稿では重複定義しない）。

### 1-2. スマホ前提で新たに要る原則: 保存で書く手を止めない

> **保存に失敗しても、書いた文章を画面から消さない。**

- **なぜこれが原則になるか**: ローカル版の保存は IndexedDB への書き込みで、実質失敗しなかった。
  サーバ化すると保存はネットワーク越しになり、**メイン利用形態がスマホ＝電波が不安定な環境**に
  なる。「保存できませんでした」で入力が消える設計は、判断軸 1（書く手を止めないか）に
  真っ向から反する。**移行によって新しく生まれるリスクなので、移行の仕様として決めておく。**

| 論点 | 決定 | なぜ |
| --- | --- | --- |
| 画面の反映 | **楽観的更新**。入力は即座に画面へ反映し、送信の完了を待たない | 往復待ちで文字入力が引っかかると使い物にならない |
| 送信の単位 | **編集した 1 件**（シーン / キャラクター / 作品）単位。作品まるごとを毎回送らない | モバイル回線の転送量と、Server Action のボディ上限（既定 1 MB）の両方に効く |
| 送信のタイミング | テキストは**確定時**（フォーカスが外れる or 一定時間の無操作）。1 キーストロークごとに送らない。具体の待ち時間は dev（目安 0.5〜1 秒） | 現行の `InlineText` が `onCommit` で確定させる作りと揃う |
| 失敗したとき | ①**入力内容を画面から消さない** ②「保存できませんでした。通信を確認してください」＋**再試行**を出す ③未保存のまま画面を離れようとしたら警告する | 3 つとも「消えない」ことのためにある |
| セッション切れで失敗したとき | 同じ扱い。再ログイン後は `callbackUrl` で同じ画面へ戻す。**戻った先で入力内容が自動復元されることは保証しない**（[13](#13-やらないことスコープ外の宣言)） | 自動復元は下書きの保存先が要る＝データモデルが増える |
| 表示 | 保存中 / 保存済み / 失敗のインジケータは**画面に 1 か所だけ**（ヘッダ） | シーンごとにバッジを出すと一望性（判断軸 2）が落ちる |

- 未保存の変更をキューに溜めて後から自動再送する仕組み（オフライン書き込み）は
  **作らない**（[9](#9-オフライン利用を保留のままにする理由チケット-9)）。ここで決めているのは
  「失敗を握り潰さない・入力を消さない」までである。

## 2. JSON 書き出し／読み込みの存廃（チケット 7）

**決定: 解釈 (b) —— 機能は残すが、バックアップの主手段としての位置づけをやめ、常用導線から外す。
`downloadProject` / `toExportJson` / `parseProjectJson` / `withFreshIds`
（[src/lib/io.ts](../../../../src/lib/io.ts)）はいずれも残す。**

> **解釈 (b) は 2026-08-04 に社長が明示回答して確定した**（決裁記録 差分 2）。
> planning 着手時点では「回答が無ければ (b)」という既定として扱っていたが、
> **根拠は既定ではなく社長判断である**。結論は変わらないが、暫定ではない。
> (a)（機能ごと廃止）を再判断するのは移行完了後で、別チケットとして扱う。

- **なぜ (b) か**: 現時点で既存作品の正本は IndexedDB のみで、`*.storyline.json` が唯一の
  避難路。移行完了前に書き出しを消すと**既存作品を DB に持ち込む手段が消える**（不可逆）。
  一方 (b) で残しておいて後から消すのは可逆。**不可逆な選択を後回しにする。**
- **社長指示の趣旨は満たす**: 「JSON で書き出すのはやめて」の実質は「バックアップのために
  毎回書き出させるのをやめたい」。DB が正本になれば書き出しは日常操作から消えるので、
  **UI 上の常用導線から外す**ことで趣旨を満たす。

### 残すもの / 外すもの

| 対象 | 扱い | 理由 |
| --- | --- | --- |
| `parseProjectJson` / `withFreshIds`（読み込み） | **残す** | 既存データの移行に必須（[5](#5-既存ローカルデータを持つユーザの導線チケット-3)） |
| `downloadProject` / `toExportJson`（書き出し） | **残す** | 退会・作品削除の前に退避させる出口が要る |
| 作品画面ヘッダの「書き出す」ボタン | **外す** | 375px のヘッダに常用しないボタンを置けない（原則 1） |
| 作品一覧ヘッダの「JSONを読み込む」ボタン | **外す** | 同上。移行時にしか使わない |
| 作品一覧カード内の「書き出す」ボタン | **残す（副次扱い）** | 作品単位の退避はここでしかできない。375px でカードに収まらないならメニュー内へ（配置はデザイン部） |
| アカウントメニュー内「JSON を読み込む」 | **新設** | 移行の入口。EmptyState が消えた後も辿れる場所が要る |
| 作品削除 / 退会の確認モーダル内の「書き出す」 | **新設** | 不可逆操作の直前が、書き出しが最も要る瞬間 |

- `EXPORT_FORMAT = "storyline.project"` と `EXPORT_VERSION = 1` は**変えない**。
  ローカル版が書き出した JSON をサーバ版が読めることが移行の生命線。

### いつ消すか

- **移行が完了し、社長が「もう JSON は要らない」と判断した時点**で、(a)（完全廃止）を別チケットで
  判断する。本移行では消さない。
- 消す条件の目安: 全利用者がサーバ版にログイン済みで、旧 IndexedDB からの取り込みが
  終わっていること。**それまでは 1 行も消さない。**
- (a) に確定した場合は
  [03-import-export.md](../../../docs/02-development-docs/03-import-export.md) も同じコミットで
  更新する（決裁記録の「注意」に記載済み）。

## 3. ログイン前に見せる画面（チケット 1）

**決定: ランディングページは作らない。`/login` 1 枚だけを作り、見出し ＋ 1 行の説明 ＋
「Google でログイン」ボタンのみを置く。**

- **なぜ**: 利用者は社長本人と声をかけた数人だけで、集客も検索流入も想定していない。
  紹介ページを作っても読む人がいない一方、文言・スクリーンショット・レスポンシブの
  保守対象が 1 画面増える。
- **なぜ 1 行の説明は残すか**: URL を渡された数人が「何のサイトか分からないまま Google 認証を
  求められる」状態は避けたい。既存の `metadata.description`
  （「シナリオの時系列とキャラクターのつながりを整理するツール」）をそのまま出せば足りる。

### `/login` の中身（375px 基準。これで全部）

```
  ┌──────────── 375px ────────────┐
  │                               │
  │          storyline            │
  │   シナリオの時系列とキャラクター  │
  │   のつながりを整理するツール      │
  │                               │
  │   [  Google でログイン  ]       │  ← 幅いっぱい・縦 48px 以上
  │                               │
  │   ログインできるのは許可された     │
  │   アカウントのみです             │  ← 許可リスト方式（決定 10）を採る前提の文言
  └───────────────────────────────┘
```

- PC でも同じ 1 カラムを中央に置くだけ。**PC 専用のレイアウトを作らない**（原則 1）。
- 利用規約・プライバシーポリシー・問い合わせは置かない（公開サービスではない）。
- ログイン失敗（許可外アカウント・OAuth エラー）は同じ `/login` 上に日本語で出す。
  Auth.js の既定エラーページは使わない（英語で出るため）。
- アカウント削除直後は「アカウントを削除しました」もこの画面に出す（[8](#8-退会データ削除チケット-6)）。

## 4. 未ログイン時のルーティング（チケット 2）

**決定: `/login` と `/api/auth/*` 以外の全ルートを保護する。未ログインアクセスは
`/login?callbackUrl=<元のパス>` へリダイレクトする。`/` を未ログインでも見える画面にはしない。**

- **なぜ**: 未ログインで見せて意味のあるデータがひとつも無い（作品はすべてユーザ紐づけ）。
  `/` を「未ログインなら紹介、ログイン済みなら一覧」に分岐させると、決定 1 で作らないと決めた
  ランディングが結局必要になる。
- **なぜ `callbackUrl` を持つか**: スマホで作品の URL を開く → ログインを挟む、という流れが
  日常的に起きる（セッション切れ・別端末）。着地点を失わせない。

| 状態 | アクセス先 | 挙動 |
| --- | --- | --- |
| 未ログイン | `/`・`/projects/*` | `/login?callbackUrl=...` へリダイレクト |
| 未ログイン | `/login` | ログイン画面を表示 |
| ログイン済み | `/login` | `/` へリダイレクト（ログイン画面は見せない） |
| ログイン済み | 他人の作品 id / 存在しない id | **404**（「権限がありません」ではなく「見つかりません」。id の存在を漏らさない） |
| セッション切れ | 任意の保護ルート | `/login?callbackUrl=...` へ。編集中の入力は自動復元しないが、**保存失敗時に画面から消しもしない**（[1-2](#1-2-スマホ前提で新たに要る原則-保存で書く手を止めない)） |

- 判定は middleware で行う（毎ページで書かない）。ただし**所有者チェックは middleware では
  やらない**。`projectId` の所有判定はデータ取得時に `userId` で絞った結果が空かどうかで行う
  （middleware から DB を引かない）。

### 4-2. セッションの有効期間

**決定: セッションは 30 日（アクセスのたびに延長する）。**

- **なぜ**: スマホがメイン利用形態で、書きたくなったときに開いて数分だけ触る使い方が中心になる。
  そのたびに Google の同意画面を挟むのは、判断軸 1（書く手を止めない）に反する。
- 「ログアウト」は明示操作としてアカウントメニューに置く（[8](#8-退会データ削除チケット-6)）。
  共用端末を想定しない個人ツールなので、自動ログアウトは短くしない。
- **未確認**: Auth.js v5 の既定セッション期間と、延長（rolling）の設定方法。dev が実装時に確認する。

## 5. 既存ローカルデータを持つユーザの導線（チケット 3）

**決定: 専用の移行ウィザードは作らない（決裁どおり）。作品 0 件のときの EmptyState を
そのまま移行導線として使い、「JSON を読み込む」を新規作成と同格に並べる。
併せてファイル選択を複数選択可（`multiple`）にする。**

- **なぜウィザードを作らないか**: 移行は 1 人あたり生涯 1 回しか通らない画面で、作るほど
  「使われないコード」が残る。既存の `parseProjectJson` / `withFreshIds` がそのまま使える。
- **なぜ複数選択を許すか**: 作品ごとに 1 ファイルなので、10 作品あると読み込み操作が 10 回に
  なる。`multiple` は input の属性 1 つ（現行 [src/app/page.tsx](../../../../src/app/page.tsx) は
  単一選択）で、移行体験の質が明確に上がる。

### 移行は「旧データが入っている端末ごと」に行う（推奨線は PC）

**決定: ローカル版を開いたことのある端末・ブラウザを洗い出し、そのすべてで全作品を書き出す。
読み込みは PC を推奨線とし、スマホからの読み込みも塞がないが動作保証はしない。**

> **草案の訂正**: 草案は「移行元データは PC の IndexedDB にしかない／スマホには移行すべき
> データが存在しない」と断定していたが、**これは事実として誤り**。IndexedDB は
> **オリジン × ブラウザ × 端末**ごとに独立しているので、ローカル版をスマホのブラウザでも
> 開いていたなら、その端末にしか無い作品が存在しうる。断定したまま切り替えると
> **その作品は復旧できない**。

- **書き出し（移行元）**: 旧データがある端末で行うしかない。**どの端末・どのブラウザで
  ローカル版を使ったかを知っているのは社長だけ**なので、切替前に洗い出してもらう（Q4）。
- **読み込み（移行先）**: PC を推奨線とする。`.json` をファイルアプリから選ぶ操作は OS ごとに
  挙動が違い、`accept="application/json,.json"` が効かない環境もありうる（**未確認**。
  実機確認は dev）。スマホからの読み込みを禁止はしない。
- これは原則 1 の例外ではなく**適用対象外**。移行は「日常操作」ではなく「旧データを引き取る
  1 回きりの作業」なので、スマホ優先の判断軸が働かない。

### 取り込み時の挙動

**決定: インポートは常に「新しい作品として増やす」。上書きは提供しない。**

- 現行の「既に開いています。上書きしますか？」の分岐（[src/app/page.tsx](../../../../src/app/page.tsx)）は
  **廃止**し、サーバ版では常に新規採番で取り込む。
- **なぜ**: 上書きは不可逆で、同じファイルを 2 回読んだだけで最新の編集が消える。重複して
  増えるのは「片方を消す」で回復できる。**可逆な失敗を選ぶ。**
- id はユーザ内で新規採番する（`withFreshIds` 相当）。旧 IndexedDB 由来の id を、他ユーザと
  共有する DB の主キーに持ち込まない。
- 旧 JSON に含まれるサムネイル（data URL）は取り込み時に Blob へ移す。DB に data URL を
  残さない（決裁どおり）。具体手順は移行方針チケットの管轄。
- **1 ファイル = 1 作品 = ひとまとまり**として扱う。途中で失敗したら**その作品は作らない**
  （中途半端な作品を残さない）。複数ファイルのうち 1 つが失敗しても、他は取り込む。
  失敗したファイル名を画面に出す。

### 移行の受け入れ条件（企画が求める合格ライン）

移行方針・本実装のどちらでも、次を満たさなければ「移行できた」と見なさない。

1. ローカル版で書き出した JSON をサーバ版で取り込み、**再度書き出す**と、
   作品 / ストーリー / シークエンス / シーン / キャラクターの**件数と並び順が一致**する。
   （並び順＝時系列そのものなので、件数だけ合っていても不合格）
2. `title` / `summary` / `timeLabel` / `place` / `status` / `memo` / `characterIds` の対応が
   崩れていない。特に `characterIds` は id を振り直すため、**張り替え後も同じ人物を指す**こと。
3. サムネイルは data URL → Blob URL に変わるため同一性ではなく「**画像が表示される**」で判定する。
4. 取り込み前後で、社長の手元の作品一覧の件数と一致する。

### 初回ログイン後の画面（作品 0 件・375px 基準）

```
  ┌──────────── 375px ────────────┐
  │      まだ作品がありません        │
  │                               │
  │  新しい作品を作るか、以前このブラウザ │
  │  で使っていた *.storyline.json を  │
  │  読み込んでください               │
  │  （PC から・複数まとめて選べます）   │
  │                               │
  │  [  ＋ 最初の作品を作る  ]        │
  │  [  JSON を読み込む  ]           │
  └───────────────────────────────┘
```

- 作品が 1 件以上あるユーザにはこの案内を出さない（移行済みなので邪魔になるだけ）。
- 「一度だけ出るお知らせモーダル」は作らない。表示済みフラグを持つ＝データモデルが増える。
- EmptyState が消えた後の入口はアカウントメニュー内「JSON を読み込む」（[2](#2-json-書き出し--読み込みの存廃チケット-7) の表）。

### 差し替えが必要な既存文言（dev 向けチェックリスト）

| 場所 | 現行 | 変更後の趣旨 |
| --- | --- | --- |
| `/` の EmptyState | 「新しい作品を作るか、書き出した JSON を読み込んでください。データはこのブラウザ内 (IndexedDB) に保存されます。」 | 上記ブロックの文面へ（「データはアカウントに保存されます」） |

## 6. ローカル版の扱いと廃止タイミング（チケット 4）

**決定: 並行運用の猶予期間は設けない。サーバ版のデプロイをもってローカル版は廃止し、
`persist` / `idbStorage` の読み書きコードは切替と同じコミットで削除する。
代わりに 4 つの安全弁で復旧可能性を担保する。**

- **なぜ猶予期間を作らないか**: 同じ URL に「ブラウザに書く版」と「サーバに書く版」が
  期間中に混在すると、どちらに書いたか分からない状態が生まれ、後から統合できないデータの
  分岐が起きる。**データが 2 か所に分かれる期間そのものが最大のリスク。**
- **なぜ IndexedDB 読み書きコードも消すか**: 残すと「サーバに繋がらないときはローカルに書く」
  という中途半端な経路を後から生やしてしまう。オフライン対応は保留（[9](#9-オフライン利用を保留のままにする理由チケット-9)）であり、
  設計が決まる前に断片を作らない。
- **保守的に見るための言い換え**: 「猶予期間を作らない」＝「急ぐ」ではない。
  **切替そのものを遅らせることはできる**（安全弁 2 が済むまでデプロイしない）。
  猶予期間なしで危険なのは「書き出しが済まないまま切り替える」ことだけなので、
  そこをリリースゲートにして塞ぐ。

### 安全弁（この 4 つで「猶予期間」の代わりとする）

**1. 切替前コミットに git タグ `local-final` を打つ**（保険。当てにしすぎない）

- checkout して `npm run dev` で立ち上げれば、そのブラウザの IndexedDB からそのまま読める。
- ただし成立条件がある。草案の「**実質の猶予は無期限**」は言い過ぎなので訂正する:
  - **同じブラウザプロファイル**であること（別ブラウザ・シークレットでは読めない）
  - **同じオリジン**であること。ローカル版を `http://localhost:3000` で使っていたなら
    `npm run dev` で一致する（**現状デプロイ先が無い前提。決裁記録の記述に依拠しており未確認**）。
    別のオリジンで使っていたなら、そのオリジンで動かす必要がある
  - **ブラウザにサイトデータを消されていない**こと。手動削除だけでなく、
    ストレージ逼迫時の自動退去もありうる
  - **dev 環境（Node / npm）を持つ人しか使えない**。招く数人には使えない安全弁である
- したがってこれは**社長本人向けの最後の保険**であって、移行手順の主役ではない。

**2. 切替デプロイ前に、旧データがある全端末で全作品の JSON を書き出す（リリースゲート）**

- **草案では「リリース手順に含める」だったが、本稿では切替の前提条件に格上げする。**
  次が確認できるまで切替デプロイを実行しない:
  - ローカル版を開いたことのある端末・ブラウザを列挙できている（[5](#5-既存ローカルデータを持つユーザの導線チケット-3)・Q4）
  - **各端末で「書き出したファイル数 = 作品一覧の件数」が一致**している
- 書き出したファイルは移行後のインポート元でもある。
  [2](#2-json-書き出し--読み込みの存廃チケット-7) で書き出し機能を残すのはこのため。

**3. IndexedDB を明示的に削除しない**

- サーバ版は `storyline-store-v1`（[src/lib/storage.ts](../../../../src/lib/storage.ts)）に対して
  読み書きとも行わないが、`del()` も呼ばない。放置された残骸を消す処理は今後も入れない（[13](#13-やらないことスコープ外の宣言)）。

**4. 切替後、旧版（`local-final`）では編集しない**

- 旧版は**読み出しと書き出し専用**として扱う。ここで編集してしまうと、猶予期間を切ってまで
  避けた「正本が 2 か所」が別経路で復活する。運用ルールとして社長に明示する（Q4 に含む）。

## 7. 作品数・シーン数・画像サイズの上限（チケット 5）

**決定: 以下の値をサーバ側（Server Action の入口）で強制する。超過したら操作を拒否し、
理由を日本語で返す。**

### 上限値

| 対象 | 上限 | 判定単位 |
| --- | --- | --- |
| **ユーザ数（＝許可リストの人数）** | **6** | サービス全体 |
| 作品 | **20** | ユーザ |
| ストーリー | **20** | 作品 |
| シークエンス | **50** | ストーリー |
| シーン | **200** | シークエンス |
| シーン合計 | **2,000** | 作品 |
| シーン合計 | **5,000** | ユーザ |
| キャラクター | **100** | 作品 |
| サムネイル | **1 枚 / シーン**、縮小後 **300 KB** まで（超えたらまず再圧縮） | シーン |
| 画像の合計容量 | **100 MB** | ユーザ |
| 取り込む画像の元ファイル | **20 MB** まで | 操作 |
| インポート 1 ファイル（JSON） | **50 MB** | 操作 |

- **ユーザ数 6 が全上限の前提**。草案はここが抜けていたが、下の概算根拠は「利用者数 × 1 人あたり
  上限」で無料枠を割っているので、**人数が増えれば他の上限がすべて無効になる**。
  DB 側が律速で、1 人あたり最悪 約 75 MB → 6 人で 450 MB（無料枠 512 MB 想定）。
  **7 人目を足すときは、本章の表を再計算してから足す。**
- 作品 20 / ユーザは容量由来ではなく整理のための値（容量を決めるのはシーン数と画像量）。
  **緩めても容量見積りは崩れない**ので、要望が出たら優先的に緩めてよい上限。
- **なぜ上限を置くか**: 無料枠を守ることが第一だが、それ以上に**壊れた JSON や誤操作で
  巨大なデータが 1 回で入る事故**を止めるため。人手の入力で上限に当たることはまず無い。
- **なぜこの粒度か**: 「ユーザ合計シーン数」だけを見ると 1 作品にすべて突っ込む形を止められず、
  「1 シークエンスあたり」だけを見ると作品を増やして回避できる。両端を押さえる。
- **書く手を止めないため**: 使用量バーや「残り N 件」の常時表示は**作らない**。上限に当たった
  ときにだけメッセージを出す（例: 「1 つのシークエンスに置けるシーンは 200 件までです。」）。

### テキスト長の上限（すべて文字数。全角半角を区別しない）

| フィールド | 上限 |
| --- | --- |
| 作品名 / ストーリー名 / シークエンス名 / シーン名 | 100 |
| ログライン・あらすじ（`summary`） | 500 |
| `timeLabel` / `place` | 100 |
| シーンの `memo` | 2,000 |
| キャラクター `name` | 50 |
| キャラクター `role` | 100 |
| キャラクター `note` | 1,000 |

### 画像は「拒否する前に再圧縮する」

**決定: 縮小後 300 KB を超えたら、まず品質を落として再圧縮し、それでも超えるなら長辺を縮める。
最終的に超えたものだけ拒否する。**

- **草案は「300 KB を超えたら弾く」だったが、企画判断として変更した。**
  スマホのカメラロールには、細かいテクスチャの多い写真（風景・雑踏）が普通に入っていて、
  長辺 640〜800px でも 300 KB を超えることはありうる。**それを「この画像は使えません」で
  返すのは判断軸 1（書く手を止めない）に反する。** サムネイルは資料画像であって原本ではないので、
  多少劣化しても目的を果たす。
- 300 KB の上限自体は残す。役割は「弾く基準」から「**再圧縮の目標値であり、
  縮小をすり抜けた画像を止める最後の栓**」に変わる。
- デコードできない形式（HEIC 等）は「この画像は読み込めません。JPEG か PNG を選んでください」と
  返す。**iOS のカメラロールは HEIC が既定なので、ここは実機確認が必須**
  （選択時に JPEG へ変換されるかは環境依存。**未確認** → dev の実機確認事項）。
  スマホがメイン想定である以上、ここが通らないと画像機能が実質使えない。

### サムネイルの公開範囲（草案に無かった論点）

**決定: v1 は「推測できない URL の公開 Blob」で許容する。署名付き URL・アクセス制御は作らない。**

- **論点**: 決裁は「各自の作品は本人だけ」だが、Vercel Blob に置いた画像は
  **URL を知っていれば誰でも取得できる**状態になる想定（**未確認**。private / 署名付きが
  無料枠で使えるなら使う。dev が契約時に確認）。厳密には決裁と衝突する。
- **なぜ許容するか**: (a) 画像はシーンの資料であって本文（あらすじ・メモ）ではなく、
  本文は DB 側で `userId` で絞られる (b) URL はランダムなパスで、一覧も検索対象にもならない
  (c) 利用者が 6 人以内の私的ツールで、対策の実装コストに見合わない。
- **社長の受容確認が要る**（Q8）。受け入れられない場合は「サムネイル機能を v1 で止める」か
  「配信をアプリ経由にする」かの二択になり、どちらもコストが上がる。

### 一望性のためにページングしない（草案に無かった論点）

**決定: ボードは開いているストーリーのシーンを**一括で**取得する。ページング・無限スクロールは
作らない。作品一覧も全件（最大 20 件）を一度に出す。**

- **なぜ**: 判断軸 2（一望性）。カンバン / 縦リストで全体が見えることがこのツールの本体で、
  「続きを読み込む」が挟まった時点で価値が壊れる。
- 1 シークエンス 200 件 / 作品 2,000 件という上限は、**この一括取得を成立させるための値でもある**。
- 開いていないストーリーは切替時に取得してよい（タブ切替は明示操作なので待ちが許容される）。

### 概算根拠

前提: 日本語 UTF-8 = 3 バイト / 文字。**想定利用者は 6 人まで**（社長 ＋ 数人。上限表の 1 行目）。

**Postgres（Neon）**

| 項目 | 計算 | 値 |
| --- | --- | --- |
| シーン 1 行のテキスト最大 | (100 + 500 + 100 + 100 + 2,000) 文字 × 3 B | 8.4 KB |
| ＋ id・FK・order・status・行ヘッダ | | 約 0.2 KB |
| ＋ インデックスと行オーバーヘッド | × 1.5 | **約 13 KB / シーン（最悪）** |
| 実運用の平均想定 | 全フィールド計 300 文字前後 × 3 B × 1.5 | **約 1.4 KB / シーン** |
| ユーザ上限まで埋めた最悪（シーン） | 5,000 シーン × 13 KB | 65 MB |
| ユーザ上限まで埋めた最悪（キャラクター） | 100 人 × 1,150 文字 × 3 B × 1.5 × 20 作品 | 約 10 MB |
| **1 ユーザあたり最悪** | 65 + 10 | **約 75 MB** |
| 5 人が上限まで埋めた最悪 | 75 MB × 5 | **約 375 MB** |
| 6 人が上限まで埋めた最悪 | 75 MB × 6 | **約 450 MB** |
| 7 人が上限まで埋めた最悪 | 75 MB × 7 | **約 525 MB（無料枠 512 MB を超える）** |
| 現実的な利用（1 人 1,200 シーン） | 1,200 × 1.4 KB × 6 人 | **約 10 MB** |

→ **Neon 無料枠 0.5 GB（512 MB）想定に対し、上限まで埋めきった最悪ケースで 6 人が限界**。
Neon は履歴保持ぶんも容量に数えるため実際の余裕はこれより小さい。現実的な利用では 1 桁 MB の
ため問題にならない。**人数か上限を緩める提案が来たら、この表を更新してから判断する。**

**Vercel Blob（スマホのカメラロールから取り込む前提）**

| 項目 | 計算 | 値 |
| --- | --- | --- |
| 取り込む元画像 | スマホの写真 | 2〜12 MB |
| **Blob へ送る前に必ずクライアントで縮小する** | 長辺 640px / JPEG q0.82（[src/lib/image.ts](../../../../src/lib/image.ts) の現行値 `MAX_EDGE` / `QUALITY`） | **約 40〜150 KB / 枚**（平均 100 KB とみなす） |
| ユーザ上限 100 MB | 100 MB ÷ 100 KB | 約 1,000 枚 |
| 6 人合計 | 100 MB × 6 | **600 MB** |

→ **Blob 無料枠 1 GB のおよそ 6 割**。DB より余裕があるので、**律速は Blob ではなく DB**。
1,000 枚はユーザ上限 5,000 シーンの 20% にサムネイルが付く計算で、実運用では十分。
**元画像の大きさは Blob 使用量に影響しない**（原本は絶対にアップロードしない）。

- **縮小の長辺 640px はモバイル実寸で再検証すること**（PC のカード幅 288px を前提にした値。
  375px 幅 × 2 倍解像度では 686px 相当が必要）。**上げる場合も 800px を超えないこと**
  （800px なら 1 枚 約 160 KB ＝ ユーザ上限で約 625 枚。上表の見積りが崩れない範囲）。
  最終判断は design / dev。
- 現行はサムネイルを **data URL** で持つ（`Scene.thumbnail`）。Blob では生バイナリになるため
  base64 の約 1.33 倍が消える。上表はバイナリ基準。

**インポート JSON の 1 ファイル上限を 20 MB → 50 MB に引き上げた理由**

- 旧 JSON は**サムネイルを data URL のまま含む**。1 枚 100 KB のサムネイルは base64 で約 137 KB に
  なるので、**サムネイル付きシーン 150 件で約 20 MB** に達する。20 MB のままだと
  **移行そのものが上限に弾かれる**（草案の値では既存作品を持ち込めない可能性があった）。
- この値はクライアント側で `parseProjectJson` に渡す前に見る値で、サーバ負荷とは無関係。
  ファイル全体を Server Action へ送る実装は Next.js のボディ上限（既定 1 MB）で必ず落ちるため、
  **クライアントで解析 → 画像は Blob へ直接アップロード → テキストは分割送信**が前提
  （設計は移行方針チケット）。

**転送量（モバイル回線を食わないこと）**

- 作品一覧（`/`）にサムネイルを出さない現行仕様を維持する（統計と更新日時のみ）。
- ボードは開いているストーリーのシーンぶんだけ読む。1 画面 20 枚 × 100 KB ＝ 約 2 MB。
- Blob の URL は内容ごとにユニークなパスになるため、長い `Cache-Control` を付けて
  ブラウザキャッシュに載せる。同じ作品を何度開いても実転送は初回のみ。

> **要確認**: 「Neon 無料枠 0.5 GB」「Blob 無料枠 1 GB」は 2026-08-04 時点の**想定値**であり、
> 企画部では確認していない。`vercel install neon` / Blob ストア作成の時点でダッシュボードの
> 実値を確認し、想定と違えば本表の上限（特に**ユーザ数**）を見直す（開放質問 Q3）。

## 8. 退会・データ削除（チケット 6）

**決定: 「アカウントを削除する」を 1 本だけ作る。データだけ消してアカウントを残す導線、
ゴミ箱、論理削除、削除の猶予期間は作らない。**

- **なぜ作るか**: 自分以外の数人のデータを預かる以上、「自分のデータを消す手段が本人の手元に
  無い」のは筋が悪い。Prisma の cascade を張れば実装は小さく、無料枠の掃除にもなる。
- **なぜ最小にするか**: 個人利用ツールで、退会は生涯 1 回。凝った確認フローや猶予期間は
  そのぶん DB に行が残り続けるだけで誰も得しない。

### 置き場所と動線

- `/settings` のような専用ページは**作らない**。`/` のヘッダのアカウントメニューに
  「ログアウト」「JSON を読み込む」「アカウントを削除」を置く。
- 「アカウントを削除」→ 確認モーダル（375px 基準）:

```
  アカウントを削除しますか？

  作品 12 件・シーン 340 件・画像 28 枚が
  すべて削除されます。元に戻せません。

  [ すべての作品を書き出す ]   ← 退避の出口（決定 2 で書き出しを残す理由）

  □ すべてのデータが削除されることを理解しました

  [ キャンセル ]  [ 削除する（危険色） ]
```

- チェックを入れるまで削除ボタンは押せない。作品名のタイプ入力までは求めない
  （生涯 1 回の操作にそこまでの摩擦は要らない）。
- 削除対象: 作品 / ストーリー / シークエンス / シーン / キャラクター / シーン⇔キャラの中間行 /
  Blob 上の画像 / Auth.js の `Account`・`Session` / `User` 行。**残さない。**
- **削除の順序は Blob → DB**。逆にすると、Blob 削除に失敗したとき URL の参照ごと消えて
  **孤児画像が無料枠を静かに食い続け、手で消すこともできなくなる**。
  Blob の削除に失敗したら中断してエラーを出す（DB に URL が残っている＝やり直せる）。
- 削除後は `/login` に戻し「アカウントを削除しました」を表示。同じ Google アカウントで
  再ログインすると、新規ユーザとして空の状態から始まる（許可リストに残っていれば）。
- 個別の作品削除は現行どおり確認 ＋ 即時削除（取り消し無し）。作品削除時にそのサムネイル
  Blob も同じ順序で消す。スマホでの誤タップを避けるため、確認は現行の `window.confirm`
  （[src/app/page.tsx](../../../../src/app/page.tsx)）ではなくモーダルにする
  （文言と配置はデザイン部）。

## 9. オフライン利用を「保留のまま」にする理由（チケット 9）

**決定: v1 ではオフライン対応をやらない。決裁の「移行完了後に再検討」を維持する。**

> **理由（これが蒸し返されたときの回答）**: サーバ移行が終わるまでは「何をキャッシュし、
> いつどちらを正とするか」が決められず、先に作ると**正本が 2 か所に分かれる**——
> [6](#6-ローカル版の扱いと廃止タイミングチケット-4) で猶予期間を切ってまで避けた状態を、自分で作り直すことになる。

- 補足として承知しておくこと: スマホがメイン想定になったぶん、電波の無い場所で開けない
  痛みは初回決裁時より確実に大きい（開放質問 Q5）。
- **v1 で用意する緩和はこれだけ**: 電波が切れて保存に失敗しても
  **書いた内容が画面から消えない**（[1-2](#1-2-スマホ前提で新たに要る原則-保存で書く手を止めない)）。
  電波が戻れば再試行で送れる。「オフラインでも新しく書き始められる」ことは v1 では実現しない。
- 再検討の入口: 移行完了後、実際に「書けなくて困った」場面が出たら、IndexedDB を
  **読み取りキャッシュとして**戻す案から検討する（書き込みキューは最後）。

## 10. 決裁の穴を埋める — サインインを許可リストで絞る

**決定: 環境変数 `AUTH_ALLOWED_EMAILS`（カンマ区切り）に列挙したメールアドレスだけログインを
許可する。未設定または不一致ならサインインを拒否し、`/login` に
「このアカウントではログインできません」と表示する。**

> **これは社長決裁に含まれていない、企画部の追加提案である。**
> 決裁は「共有範囲（本人のみ）」を決めているが「**誰がサインアップできるか**」を決めていない。
> 決裁記録にも「サインインを許可できる人 = 要社長入力（新規論点）」として記録済み。
> **方式そのものの承認が要る**（Q1 はアドレスの列挙だけでなく、この方式の承認も含む）。

- **なぜ必要か**: Google ログインを素で開けると、URL を知った誰でもアカウントを作れて
  無料枠（[7](#7-作品数シーン数画像サイズの上限チケット-5)）を消費できる。ユーザ数 6 という
  上限の前提も崩れる。**無料枠を守る唯一の防波堤がここ。**
  - なお「無料枠を超えたときに課金になるか、停止・スロットルになるか」は**未確認**
    （Vercel / Neon の無料プランの挙動。dev が契約時に確認する）。
    課金にならなくても、**本来の利用者が使えなくなる**時点で塞ぐ理由は十分ある。
- **なぜ許可リストか（招待コード等ではなく）**: 利用者が 6 人以内と分かっているので、
  Auth.js の `signIn` コールバック数行で足り、DB のテーブルも管理画面も要らない。
- **メールアドレスの一致だけを条件にしない**。Google 側で**検証済みのアドレス**であることも
  条件にする（取得できるかは dev が Auth.js のプロフィールで確認。**未確認**）。
- 人を増やすときは環境変数に 1 行足して再デプロイする。招待 UI は作らない。
  **列挙できる人数の上限は 6**（[7](#7-作品数シーン数画像サイズの上限チケット-5) の見積り）。
- **未設定時は全拒否**（全許可にすると設定忘れがそのまま穴になる）。
- **この方式が却下された場合の代替**: ①誰でもログイン可 ＋ 使用量監視（枠を食われてから気づく
  ので企画としては非推奨） ②招待コード（DB とコード管理が増える）。どちらもコストか
  リスクが上がるので、許可リストを推す。

→ 許可リストに入れるアドレスと、方式そのものの承認は社長判断（開放質問 Q1）。

## 13. やらないこと（スコープ外の宣言）

判断コストを下げるため明示する。以下が欲しくなったら、**この spec を更新してから**着手する。

- ランディングページ / 紹介ページ / 利用規約 / プライバシーポリシー
- 招待 UI・メンバー管理・作品の共有・公開リンク・共同編集
- Google 以外のログイン（メール＋パスワード / Magic Link / GitHub）
- オフライン編集・PWA・Service Worker・プッシュ通知
- ゴミ箱・論理削除・版管理・変更履歴・元に戻す
- 編集競合の検知と解決（最終書き込み優先で始める）
- **保存失敗時の自動再送**と、**別ページへ遷移した後の入力内容の復元**
  （※**画面に入力を残すこと自体は MVP に含む**。[1-2](#1-2-スマホ前提で新たに要る原則-保存で書く手を止めない)。
  草案はここを単に「セッション切れ時の入力内容の復元」としており、
  「保存に失敗したら入力が消えてよい」と読めたため書き分けた）
- メール通知・お知らせバナー・一度だけ出るモーダル
- 使用量ダッシュボード・課金・プラン
- ローカル版との並行運用、IndexedDB 残骸の自動削除
- 移行専用ウィザード（決裁どおり JSON 経由で済ませる）
- シーンあたり 2 枚以上のサムネイル、画像の原本保存
- Blob の署名付き URL / アクセス制御（v1 は公開 URL。[7](#7-作品数シーン数画像サイズの上限チケット-5)）
- 作品の他アカウントへの移譲（JSON 書き出し → 別アカウントで読み込みで代替）
- ネイティブアプリ / アプリストア配信（モバイルファーストは Web のまま実現する）
