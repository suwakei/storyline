## 1. 関係（エッジ）が持つ属性（論点 1）

**決定: エッジは「ラベル（自由テキスト）」と「向き（3 値）」だけを持つ。線種・色・太さ・
強度（重み）は v1 では持たない。**

### 持つもの

| 属性 | 決定 | なぜ |
| --- | --- | --- |
| ラベル | **自由テキスト 1 本**。空文字も許す | 参照ビジュアルのエッジラベル（「REST」「HTTP」）に相当。`timeLabel` と同じ思想で、語彙を固定しない。「兄」「かつての師」「終盤で裏切る」まで 1 つの欄で書ける |
| 向き | **`forward`（片方向）/ `both`（双方向）/ `none`（無向）の 3 値**。既定は `forward` | 参照ビジュアルは有向矢印。ただし「幼馴染」のような対称な関係を片方向で描くのは嘘になる。**データは常に `fromId → toId` の順で 1 本だけ持ち、向きは矢印の描き方だけを変える** |

- **「双方向」を 2 本のエッジで表現しない**。2 本にすると、片方だけ消えた状態・片方だけラベルが
  違う状態が作れてしまい、削除漏れと表示の不整合の温床になる。**1 本 + 向きの属性**に統一する。
- 同じ 2 人の間に**複数のエッジを許す**（「兄」と「憎んでいる」は別の関係）。重複を防ぐ検証はしない。
- **自己ループ（`fromId === toId`）は許さない**。描画が破綻し、「自分と自分の関係」に意味が無い。
  読み込み時に見つけたら捨てる（[6](#6-書き出し-json-への含め方と旧-json-互換論点-6)）。

### v1 で持たないもの（理由つき）

| 属性 | なぜ持たないか |
| --- | --- |
| 線種（実線 / 点線 / 二重線） | 「点線＝何か」を決めるのは作者ごとに違い、**凡例（legend）が必ず必要になる**。凡例は画面の面積を食い、375px では図の面積を直接削る。ラベルで書けば凡例なしで伝わる |
| 色 | 同上。かつ storyline の色は「キャラクター識別色」という**既存の意味**を持っており、エッジに別の意味の色を足すと 1 画面に 2 系統の色の意味が同居する |
| 強度・重み（数値） | 「関係の強さ 3」が何を意味するかを作者が定義できない。判断軸 3（データを増やす価値があるか）を満たさない |

エッジの見た目（1 種類の線をどう描くか、ラベルを線の中央の箱に乗せるか）はデザイン部が決める。
**エッジの色をキャラクター識別色から導出するかどうかも表示上の判断**であり、データは増えない。

### 削除の確認

**関係 1 本の削除も確認を挟む。** 作者が書いたラベルが消えるため、既存の「破壊的操作は必ず
ユーザ確認を挟む」原則（[.claude/CLAUDE.md](../../../CLAUDE.md)）の対象とする。
確認 UI の形式（`window.confirm` かモーダルか）と文言はデザイン部。

## 2. ノード座標の持ち方（論点 2）

**決定: 手動配置し、座標を保存する。ただし保存されるのは「ユーザが実際に動かしたノード」だけ。
一度も動かしていないノードは座標を持たず、決定的な既定位置に置く。**

### なぜ手動配置か

社長の指示は「**画面上でノードを配置し**、ノード同士をドラッグで結線して作れるようにする」
（決裁記録）。配置そのものが作者の表現（主人公を中心に置く、敵陣営を右に固める）なので、
**継続的な自動レイアウトは採らない**。キャラを 1 人足すたびに図全体が組み替わると、
「自分が作った図」でなくなる。

### なぜ「動かすまで保存しない」か

- **相関図を開いただけで作品データに書き込みが起きるのを避けるため。** ストアの更新は
  `editProject` を通り `updatedAt` を進める仕様
  （[02-data-model-and-persistence.md](../../../docs/02-development-docs/02-data-model-and-persistence.md)）
  で、作品一覧は更新日時順に並ぶ。**見ただけで一覧の並びが変わるのは誤りである。**
- 旧 JSON（座標なし）をそのまま開けるようになる。読み込み時に座標を埋める処理が要らない。

### 既定位置の要件

- 未配置のノードは、**同じデータなら毎回同じ位置**に置くこと（乱数を使わない）。
  開くたびに配置が変わると、作者が図を記憶できない。
- 未配置のノード同士が**重ならない**こと。
- 算出根拠にはキャラクターの**配列順**を使ってよい（配列順＝追加順で、末尾追加なので既存の
  未配置ノードの位置はずれない）。**キャラクターを削除すると、後続の未配置ノードの既定位置は
  ずれる**。これは許容する（未配置＝まだ作者が触っていない）。具体的な配置アルゴリズムは
  design / dev。
- **「配置をリセットして並べ直す」機能は v1 では作らない**（[14](#14-v1-スコープ)）。
  誤って動かしたノードは手で戻せる。

### 保存しないもの

**ズーム倍率・パン位置・選択中のノード・フォーカス状態は保存しない。**
端末ごとに画面幅が違うため、375px で保存した倍率を PC で復元しても意味が無い。
相関図を開くたびに「全体が収まる倍率」から始める。
（`activeStoryId` / `openSceneId` を保存していない既存方針と同じ扱い
—— [01-architecture-design.md](../../../docs/02-development-docs/01-architecture-design.md) §2）

参照ビジュアルの「リセット (⟳)」ボタンを採る場合、その意味は
**「初期表示（全体が収まる倍率・位置）に戻す」**であり、**ノードの配置は戻さない**。

### 座標の置き場所

**型のどこに置くか（`Character` 直下か、別のレイアウト型か）は dev の決定事項**
（dev 移行方針チケット「決めること 1」）。企画部が要求するのは
「キャラクター 1 人につき最大 1 組の座標が保存され、書き出し JSON を往復しても
相対的な位置関係が保たれること」だけ。

> 企画部からの判断材料（決定を拘束しない）: 座標を `Character` 直下に置くと、
> `withFreshIds` の id 張り替えと `deleteCharacter` の掃除が**既存経路のまま**で済み、
> 「キャラは居るのに座標が無い / 座標だけ残る」という不整合が構造的に発生しない。
> 別配列に分けると不整合の種類が 2 つ増える。**壊れにくさでは `Character` 直下が有利**。

## 3. 相関の粒度（論点 3）

**決定: 相関図は作品につき 1 枚。ストーリー（本編 / 外伝）別にも、時点別にも分けない。**

- **なぜストーリー別にしないか**: キャラクターは作品直下にあり、本編と外伝で共通
  （[types.ts](../../../../src/lib/types.ts) の `Project.characters`）。相関図だけストーリー別に
  すると、キャラを 1 人足すたびに N 枚の図を直すことになり、判断軸 1（書く手を止めない）に反する。
- **なぜ時点別にしないか**: storyline は**実日付を持たない**
  （[01-storyline-concept.md](../../../docs/01-project-overview/01-storyline-concept.md)）。
  時点を指す手段はシーンの並び順しか無く、相関を「シーン N 時点」に紐づけると
  **シーンを並べ替えるたびに相関の意味が変わる**。設計の核を崩す。
- **関係の変化はラベルで書く**。「味方 → 終盤で敵対」を 1 つのラベルに書けば足りる。
  `timeLabel` が「事件当日 早朝」を自由テキストで書くのと同じ考え方。

ストーリー別の相関図は v2 候補として残す（[15](#15-v2--将来)）。

## 4. `Scene.characterIds` との関係（論点 4）

**決定: 共演から線を自動で引かない。相関は完全に手動。逆向きにも影響させない
（相関図の操作で `Scene.characterIds` は 1 件も変わらない）。**

- **なぜ自動で引かないか**:
  1. **共演 ≠ 関係**。同じ部屋に居ただけのキャラ同士に線が引かれる。
  2. **一望性が壊れる**（判断軸 2）。主要シーンに 5 人出れば、そのシーンだけで最大 10 本の線が
     生える。数十シーンぶんが重なった図は読めない。
  3. 自動線を「消せる」ようにすると、**消したという事実を保存する必要が出てデータが増える**
     （判断軸 3）。自動と手動が混ざった図は、どの線が作者の意図かも分からなくなる。
- **`Scene.characterIds` は今までどおりシーンの登場人物**であり、相関図とは**別の情報**として
  並存する。相関図が参照するのは `Project.characters`（誰が居るか）だけ。

共演データの活用（「共演回数が多いのに線が無いペア」のサジェスト、ノード選択時の登場シーン一覧）は
**v1 スコープ外・v2 候補**。相関図が実際に使われ始めてからでないと価値を測れない。

## 5. 配置場所（論点 5）

**決定: 作品画面 `/projects/[projectId]` の中で、メイン領域の表示を「構成」↔「相関図」で
切り替える。新しいルートは作らない。ドロワーにも入れない。**

```
ヘッダ（作品名 / キャラクター / 書き出す）
─────────────────────────────
[ 構成 ] [ 相関図 ]          ← モード切替（ストーリータブより上位）
─────────────────────────────
「構成」時 : ストーリータブ + カンバン（md 以上）/ 縦リスト（md 未満）
「相関図」時: 相関図キャンバス（ストーリータブは出さない）
```

- **なぜルートを増やさないか**: 既存原則「**画面遷移は 2 つだけ**（一覧 ↔ 作品画面）」
  （[01-architecture-design.md](../../../docs/02-development-docs/01-architecture-design.md) §4）。
  戻る操作・リロード時の復元・404 の扱いが増えるコストに見合わない。
- **なぜドロワーに入れないか**: `Drawer` は `w-full max-w-md`（448px）で
  （[ui.tsx](../../../../src/components/ui.tsx)）、PC で相関図を描くには狭すぎる。
  そもそもドロワーの用途は「**カンバンを見たまま**編集する」ことだが、相関図を見ながら
  カンバンを触る場面が無い。用途が合わない。
- **なぜストーリータブと同列に置かないか**: ストーリータブは本編 / 外伝の切替であり、
  並べ替え・削除の対象になる。相関図は**作品共通**（[3](#3-相関の粒度論点-3)）なので、
  そこに混ぜると「相関図タブを削除できるように見える」という誤解を生む。**タブより上位に置く。**
- 相関図表示中は**ストーリータブを隠す**（相関図は本編 / 外伝を区別しないため。開放質問 Q6）。
- **どのモードで開いていたかは保存しない**。リロードすると「構成」に戻る
  （`activeStoryId` を保存していないのと同じ扱い）。

### 既存機能との役割分担（作り直さないための境界）

| やりたいこと | どこでやるか |
| --- | --- |
| キャラクターの追加 / 名前・立ち位置・メモ・識別色の編集 / 削除 | **既存の `CharacterPanel`（キャラクター管理ドロワー）に一本化**。相関図側に同じ入力欄を作らない |
| ノードの配置、関係の追加 / ラベル編集 / 削除、グループ枠の作成・割り当て | **相関図** |
| シーンへの登場人物の紐づけ | 既存の `SceneEditor`（変更なし） |

- 相関図でキャラクターが 0 人のときは、**キャラクター管理ドロワーを開く導線**を出す
  （何もできない空画面にしない）。文言と形式はデザイン部。
- 相関図からキャラクター管理へ移動できること（ノードを選んで「このキャラクターを編集」等）は
  design の裁量。**相関図内でキャラ本体を編集できるようにはしない。**

## 6. 書き出し JSON への含め方と旧 JSON 互換（論点 6）

### 書き出し

**決定: 相関データは `Project` の一部として書き出しに含める。エンベロープ
（`format` / `version` / `exportedAt` / `project`）は変えない。**

- `EXPORT_FORMAT = "storyline.project"` と `EXPORT_VERSION = 1` は**据え置く**。
  `accounts-and-server` の決定（干渉点 I-2）で「ローカル版が書き出した JSON をサーバ版が
  読めること」が移行の生命線とされており、そこに触らない。
- **据え置いてよい根拠**: 今回の変更は**フィールドの追加のみ**で、既存フィールドの意味も
  構造も変えない。既存の正規化は「読めた値だけ上書き、無ければ既定値」
  （[03-import-export.md](../../../docs/02-development-docs/03-import-export.md)）なので、
  新旧どちらの JSON も同じ読み取り経路で扱える。
- `toExportJson` / `downloadProject` は `project` をそのまま包むだけなので、
  **相関データを `Project` 配下に置く限り書き出し側の変更は不要**（企画部が
  [io.ts](../../../../src/lib/io.ts) を読んで確認済み）。

### 旧 JSON（相関データを持たない既存ファイル）の読み込み

**決定: エラーにしない。「相関データが無い作品」として読み込む。**

| 読み込む値 | 無い / 不正なときの挙動 |
| --- | --- |
| 関係の配列 | **空配列**として読む |
| グループの配列 | **空配列**として読む |
| ノード座標 | **未設定**として読む（既定位置に置く。[2](#2-ノード座標の持ち方論点-2)） |
| 座標が片方だけある（x はあるが y が無い 等） | **両方とも未設定**として扱う（片方だけの座標は意味が無い） |
| 座標が数値でない / `NaN` / `Infinity` | **未設定**として扱う |
| 関係の向きが既知の 3 値でない | **`forward`** に落とす（`status` を `idea` に落とす既存の流儀と同じ） |
| 関係の `fromId` / `toId` が**既知のキャラクター id でない** | **その関係を捨てる**（`normalizeScene` が `knownCharacterIds` で絞る流儀と同じ） |
| 関係の `fromId === toId`（自己ループ） | **その関係を捨てる**（[1](#1-関係エッジが持つ属性論点-1)） |
| キャラクターの所属グループ id が**既知のグループ id でない** | **未所属**として読む（**キャラクター自体は捨てない**） |

**旧 JSON を読み込んだ結果は「全キャラクターが既定位置に並び、線が 1 本も無い相関図」。
これが正常な初期状態**であり、エラー表示も警告も出さない。

> **dev への具体的な注意**（企画部が [io.ts](../../../../src/lib/io.ts) を読んで確認した事実）:
> 現在 io.ts にある型ガードは `str` / `isRecord` / `arr` の 3 つだけで、**数値を安全に読む
> ヘルパが無い**。座標を読むには同じ語彙で `num` 相当を足す必要がある
> （`typeof v === "number" && Number.isFinite(v)`）。`as` で通さないこと。

### 新 JSON を旧版（`local-final` 相当）が読んだとき

**相関データは黙って落ちる。落ちても既存作品は壊れないが、
「読み込んで編集し、書き出し直す」と相関データは失われる。**

- 根拠（企画部がコードを読んで確認）: `normalizeProject` は `createProject` の既定値をベースに
  **既知のフィールドだけ**をコピーし、`normalizeCharacter` も
  `id` / `name` / `role` / `note` / `color` しか拾わない。**未知のキーは無視される**ため、
  例外にはならず、静かに消える。
- **この挙動は受容する。** 旧版を「読み出しと書き出し専用として扱い、切替後は編集しない」ことは
  `accounts-and-server` spec の安全弁 4 で既に運用ルールになっている。
  ここでも同じルールが効く。
- ただしこれは**データ消失そのもの**なので、[12](#12-データを増やすことの移行コストとデータ消失リスク)
  にリスクとして明記し、dev の移行方針チケットで前方互換の判定対象とする。

### id の張り替え（`withFreshIds`）

**決定: 関係とグループも新しい id を振り、キャラクターへの参照を新旧マップで張り替える。**

- 対象: 関係の id / 関係の `fromId`・`toId` / グループの id / キャラクターの所属グループ id。
- **張り替え漏れは「線は残っているが誰を指しているか分からない」状態＝相関の破壊**を意味する。
  dev の移行方針チケットの完了条件に既に入っている項目。

### 件数の上限

**v1（ローカル版）では関係・グループの件数上限を設けない。** ローカル版は作品数にもシーン数にも
上限を持っていないため、相関データだけに上限を置くのは一貫しない。
サーバ版へ載せる段では `accounts-and-server` spec の上限表
（キャラクター 100 / 作品 など）に相関データの行を**追記する必要がある**。
**その値は本稿では決めない**（根拠となる無料枠の実値が未確定のため。同 spec Q3）。
dev が移行方針チケットで Prisma 側の受け皿を設計する際に、企画部へ差し戻すこと。

## 7. グループ枠の仕様（入れ子可否の結論）

**決定: グループ枠は入れ子にしない（単層）。1 キャラクターは同時に最大 1 グループにしか属さない。**

| 論点 | 決定 | なぜ |
| --- | --- | --- |
| 入れ子 | **しない（単層）** | 参照ビジュアルが「枠は入れ子ではなく単層」。入れ子にすると親子の循環検出・重なり順の計算が要り、375px では入れ子の枠線だけで図が埋まる |
| 複数所属 | **1 キャラは 0 or 1 グループ** | 枠で「囲む」表現である以上、2 つの枠に同時に囲まれる図は物理的に描けない（参照ビジュアルにも重なり合う枠は無い）。「〇〇家かつ騎士団」を書きたい場合は**関係（エッジ）で表現する** |
| 枠の位置・大きさ | **持たない。メンバーノードの外接矩形から自動算出する** | 枠の座標を別に持つと「枠の外にメンバーが居る」状態を作れてしまい、整合を保つ処理が要る。自動算出なら常に整合する |
| 枠の色 | **持たない** | 判断軸 3。線は既存の `line` トークン、ラベルは `muted` で足りる（最終判断はデザイン部） |
| 空のグループ（メンバー 0） | **作れる**。ただし枠として描けないため、図上の扱いはデザイン部が決める | 「先に枠を作ってから人を入れる」流れを塞がない |
| グループの削除 | 所属していたキャラクターは**未所属に戻る。キャラクター自体は消えない** | 枠は分類であって所有ではない。確認は挟む（破壊的操作の原則） |

グループが持つのは **id と名前（ラベル）だけ**。参照ビジュアルの「ブラウザ」「Fly.io」に相当する
枠の左上ラベルが、storyline では「王国側」「〇〇家」になる。

## 8. スマホ幅 375px でどう成立させるか

> **結論: 375px でも閲覧と編集の両方ができる。ただし「ノードからノードへドラッグして結線する」
> 操作を、スマホでの必須経路にしない。**

相関図は本来 PC の広い画面向きの機能であり、ここが本仕様の最大の緊張点である。
一方でこのプロダクトは**モバイルファースト**（PC とスマホで競合したらスマホを優先する。
[accounts-and-server spec 1 章](2026-08-04-accounts-and-server-spec.md)）であり、
**「PC でしかできない操作」を作ることは選べない**。

### 正直に認める制約

375px の画面に、名前と立ち位置が読めるサイズのノードを 10 個並べて全部読ませることは
**物理的にできない**。これをごまかさず、**2 段構え**で解く。

| 段 | 何を見るためのものか | 375px での状態 |
| --- | --- | --- |
| **全体表示** | 図の**構造**（誰が中心か、どの陣営がどこに固まっているか） | ズームアウトして全体を収める。ノード内の文字は読めなくてよい。色と配置と枠で構造を掴む |
| **フォーカス表示** | 特定のキャラクターの**つながり** | 1 人を選ぶと、そのキャラクターと**直接つながっている相手だけ**を表示する。文字が読める倍率になる |

- **フォーカス表示は v1 に含める。** 375px で相関図を「読める」状態にする主手段であり、
  かつ storyline の本体価値（キャラクターのつながりの一望）そのもの。
  **表示のフィルタなのでデータは増えない。**
- 全体表示とフォーカス表示は**ワンタップで往復**できること。
  （縦リストの「すべて折りたたむ / 開く」トグルが目次モードと詳細モードを往復させるのと同じ発想）

### 375px でできなければならないこと（PC 限定機能を作らない）

1. ノードを動かして配置する
2. 関係を追加する / ラベルを編集する / 削除する
3. グループ枠を作る / 名前を変える / キャラクターを割り当てる / 削除する
4. 全体表示とフォーカス表示を往復する

### 結線操作: スマホではドラッグを必須にしない

- **タップ 2 段階の経路を必ず用意する**: ノードを選ぶ →「関係を追加」→ 相手を選ぶ → ラベルを入れる。
  この経路はマウスでも使える。
- ドラッグ結線は**PC の高速手段として併存させてよい**が、375px での唯一の手段にしない。
  具体的な手順設計（どこを掴む / どう離す / 誤操作をどう戻す）はデザイン部。
- **先例**: 縦リストではドラッグ並べ替えを採らず、ボタンとドロワー内の選択に置き換えている
  （[design/ui-specs/2026-08-04-mobile-vertical-list.md](../../design/ui-specs/2026-08-04-mobile-vertical-list.md) 決定 4・5）。
  同じ判断軸をここでも適用する。

### ノードの移動は 375px でもドラッグで行う（縦リストとの違い）

- 縦リストでドラッグを捨てた理由は「**並べ替えの軸とスクロールの軸が同じ**で区別できない」こと。
  相関図では「**ノードを掴む＝移動 / 背景を掴む＝パン**」と、掴む対象で区別できるため事情が違う。
- ただし**ノードのドラッグとキャンバスのパンの取り違え**は新しい緊張点になる。
  タップ領域（44×44px 以上）とあわせて、design / dev が実機で確認すること
  （[16](#16-未確認のまま残したこと)）。

### 関係リスト（エッジ編集の代替経路）

**v1 に含める。** 「A → B: ラベル」の一覧から、関係の追加・ラベル編集・削除ができること。

- **なぜ必要か**: 375px で細いエッジ線やラベル箱を正確にタップするのは現実的でない。
  ラベル箱を 44px 角にすれば図が箱で埋まる。**リストは 375px でエッジを選ぶ唯一の現実的な手段。**
- 一覧の並び順は保存された配列順（時系列ではない）。表示上の並べ替え（キャラ別など）は design 裁量。
- 置き場所（ドロワーか、キャンバスと切り替える別ペインか）はデザイン部。

### 図の画像コピーは v1 では作らない（企画判断）

参照ビジュアルの操作コントロール 5 種のうち、**「コピー」（図の画像化・クリップボード転送）は
v1 スコープ外**とする。理由: 相関図は「作って参照する」ためのもので、外部へ持ち出す用途が
まだ確認できていない（判断軸 3）。画像化はブラウザ API の実装コストと、375px での出力サイズの
検討が別途必要になる。

**残り 4 種（全画面 / パン十字 / リセット / ズーム）の採否はデザイン部が判断する。**
ただし「リセット」の意味は [2](#2-ノード座標の持ち方論点-2) で定義済み（配置は戻さない）。

## 9. ノードの中身

**決定: ノードに出すのは「キャラクター名 ＋ 立ち位置（`role`）＋ 識別色（`color`）」。
すべて既存フィールドで、データは増えない。**

- 参照ビジュアルの「ノード内は 1〜3 行のテキスト（太字の名前 ＋ 補足行）」に対応する。
  storyline では「名前（太字）＋ 立ち位置」の 2 行になる。
- 識別色は `CHARACTER_COLORS`（10 色）由来の**「データとしての色」の例外**として扱う
  （既存のシーンチップ・縦リストと同じ扱い）。**新しい色を増やさない。**
- `note`（メモ）はノードに出さない。長文が入りうるため、図の可読性を壊す。
- **キャラクターの画像は v1 では持たない**。現行 `Character` に画像フィールドは無く、
  追加はデータモデルの拡張（かつサムネイル同様の容量問題）になる。[15](#15-v2--将来) 参照。
- **全キャラクターが必ずノードになる。**「相関図に出さない」フラグは持たない（判断軸 3）。
  端役が増えると図が混むトレードオフは認識しており、実際に困ってから v2 で扱う（開放質問 Q1）。

## 10. データモデルに要求する追加項目

**この節は dev の移行方針チケットが単独で着手できる粒度で書く。
フィールドの意味と必須 / 任意は本稿の要求であり動かさない。型の分割・置き場所・
永続化の実装方法は dev の決定事項。**

### 10-1. 新規の型

#### `Relationship`（関係 / エッジ）

| フィールド | 型 | 必須 / 任意 | 意味 |
| --- | --- | --- | --- |
| `id` | `string` | **必須** | 関係の同一性。採番規則は既存の `newId()`（`nanoid(12)`）に合わせる |
| `fromId` | `string` | **必須** | `Character.id`。矢印の根元。`toId` と同じ値は不正 |
| `toId` | `string` | **必須** | `Character.id`。矢印の先 |
| `label` | `string` | **必須（空文字を許す）** | 関係の説明。自由テキスト（「兄」「終盤で裏切る」）。既存の `title` / `summary` と同じく空文字を既定値とする |
| `direction` | `"forward" \| "both" \| "none"` | **必須** | 矢印の描き方。既定 `"forward"`。データ上の向きは常に `fromId → toId` |

- 置き場所の要求: **作品直下**（`Project` 配下）に配列で持つこと。フィールド名は
  `relationships` を推奨。ストーリー配下には置かない（[3](#3-相関の粒度論点-3)）。
- 配列の順序に意味は無い（時系列ではない）。ただし表示の安定のため**配列順を保つ**こと
  （並べ替えのたびに図が変わるのを避ける）。

#### `CharacterGroup`（グループ枠）

| フィールド | 型 | 必須 / 任意 | 意味 |
| --- | --- | --- | --- |
| `id` | `string` | **必須** | グループの同一性。`newId()` 採番 |
| `name` | `string` | **必須（空文字を許す）** | 枠の左上に出すラベル（「王国側」「〇〇家」） |

- 置き場所の要求: **作品直下**に配列で持つこと。フィールド名は `characterGroups` を推奨
  （`groups` は一般的すぎて衝突しやすい）。
- **枠の座標・サイズ・色・親グループは持たない**（[7](#7-グループ枠の仕様入れ子可否の結論)）。

### 10-2. 既存の型に足す項目

#### `Character`

| フィールド | 型 | 必須 / 任意 | 意味 |
| --- | --- | --- | --- |
| `x` | `number` | **任意** | 相関図キャンバス上の論理座標（ズーム倍率を含まない）。`y` と対で意味を持つ |
| `y` | `number` | **任意** | 同上 |
| `groupId` | `string` | **任意** | 所属する `CharacterGroup.id`。未設定なら未所属。**最大 1 つ**（[7](#7-グループ枠の仕様入れ子可否の結論)） |

- **任意である理由**: 既存データ（旧 JSON / 既存の IndexedDB）には存在しないため。
  `undefined` は「未配置 / 未所属」を意味し、正常な状態である。
- `x` / `y` は**両方揃っているときだけ有効**。片方だけなら両方とも未設定として扱う
  （[6](#6-書き出し-json-への含め方と旧-json-互換論点-6)）。
- **座標を `Character` 直下に置くか別のレイアウト型に分けるかは dev の決定**。
  分ける場合も、上の 3 項目が満たす意味と必須 / 任意は変えないこと。
- `groupId` を `Character` 側に持つのは、**同じキャラクターが 2 つのグループのメンバー配列に
  同時に載る状態を型として作れなくする**ため（グループ側に `memberIds` を持たせると、
  「最大 1 グループ」という制約を実行時にしか守れない）。

#### `Project`

| フィールド | 型 | 必須 / 任意 | 意味 |
| --- | --- | --- | --- |
| `relationships` | `Relationship[]` | **任意**（読み込み時は無ければ空配列） | 作品の関係の全体 |
| `characterGroups` | `CharacterGroup[]` | **任意**（同上） | 作品のグループ枠の全体 |

- **新規作成する作品では空配列で初期化してよい**（`createProject`）。
  型として `?` を付けるかどうかは dev 判断だが、**旧データ（存在しない）を読めることが要求**。

### 10-3. 持たないもの（明示）

- エッジの線種 / 色 / 太さ / 強度・重み
- グループの色 / 座標 / サイズ / 親グループ / メンバー配列
- ズーム倍率 / パン位置 / 選択状態 / フォーカス中のキャラ / 表示モード（構成 ↔ 相関図）
- キャラクターの画像
- 「相関図に出さない」フラグ
- 相関図そのものの名前・複数枚を区別する id（作品 1 枚のため不要）
- 実日付を持つ項目（`createdAt` / `updatedAt` 以外の日付列を足さない）

## 11. 参照整合性（削除時の掃除）

現行の `deleteCharacter` は「キャラクターを消したら全シーンの `characterIds` からも外す」
（残すとカードに幽霊チップが出るため）。**同じ流儀を相関データにも適用する。**

| 操作 | 掃除する対象 |
| --- | --- |
| キャラクターの削除 | そのキャラクターを `fromId` または `toId` に持つ**関係をすべて削除する**。（所属グループは `Character` 側に持つため、キャラごと消えて自然に解消する） |
| グループの削除 | そのグループを指す**キャラクターの `groupId` をすべて外す**。キャラクター自体は消さない |
| 関係の削除 | その関係のみ。キャラクターにもグループにも影響しない |

- **キャラクター削除の確認文言を更新する必要がある。** 現行は
  「各シーンからも外れます」（[CharacterPanel.tsx](../../../../src/components/CharacterPanel.tsx)）。
  相関図の関係も消えるようになるため、**それが伝わる文言に変える**こと。
  正確な文言はデザイン部。**ここを直さないと「知らないうちに相関が消えた」体験になる。**
- 読み込み時にも同じ整合を取る（[6](#6-書き出し-json-への含め方と旧-json-互換論点-6) の表）。

## 12. データを増やすことの移行コストとデータ消失リスク

**企画部の必須併記。** 本フィーチャは**既存フィールドの意味を一切変えず、追加だけ**で成立する。
それでも次のリスクがある。

| 増えるもの | 移行コスト | データ消失リスク |
| --- | --- | --- |
| `Character.x` / `y` / `groupId`（任意 3 つ） | 既存データでは `undefined`。読み込みの正規化に読み取りを足す | **中**。正規化への追加を忘れると、**書き出し → 読み込みの往復で配置とグループ所属だけが静かに消える**（型エラーにならないため気づきにくい。[03-import-export.md](../../../docs/02-development-docs/03-import-export.md) が同じ罠を警告している） |
| `Project.relationships` | 新規配列。正規化 / id 張り替え / キャラ削除時の掃除の**3 か所**に追随が要る | **高**。①正規化の取りこぼし＝相関まるごと消失 ②id 張り替え漏れ＝「線はあるが誰を指すか分からない」 ③削除時の掃除漏れ＝幽霊エッジ |
| `Project.characterGroups` | 同上（掃除は `groupId` を外す側） | 中 |
| **旧版（`local-final` 相当）が新 JSON を読む** | — | **高。相関データが黙って落ちる**（[6](#6-書き出し-json-への含め方と旧-json-互換論点-6) で確認済み）。旧版で読み込み → 編集 → 書き出しをすると相関が失われる |
| 書き出し JSON のサイズ | — | 低。**概算**: 関係 1 件は `JSON.stringify(_, null, 2)` のインデント込みで概ね **150〜200 バイト**（id 12 文字 ×3・ラベル日本語 3〜10 文字の場合）。100 件でも **20 KB 程度**で、サムネイル 1 枚（100 KB の画像が data URL で約 137 KB —— [accounts-and-server spec 7 章](2026-08-04-accounts-and-server-spec.md)）より小さい。上限を設けない判断（[6](#6-書き出し-json-への含め方と旧-json-互換論点-6)）の根拠 |

- **`STORAGE_KEY`（`storyline-store-v1`）を変えないこと**は本稿の要求。
- `partialize` の対象を**減らさない**こと（`projects` が保存対象から外れると作品が消える）。
- `persist` の `version` を上げるかどうか、`migrate` をどう書くかは **dev の決定**。
  本稿では指定しない。

---

## 13. 実日付を持たない設計との関係

**本フィーチャは storyline の設計の核を崩さない。**

- 相関データに**日付フィールドを一切足さない**（[10-3](#10-3-持たないもの明示)）。
- 「関係がいつ変わったか」は**ラベルの自由テキスト**で表す（`timeLabel` と同じ思想）。
- 相関を時点に紐づけない（[3](#3-相関の粒度論点-3)）ため、**シーンを並べ替えても相関の意味は
  変わらない**。

## 14. v1 スコープ

### 作るもの

1. 作品につき 1 枚の相関図。作品画面のモード切替（構成 ↔ 相関図）で開く
2. 全キャラクターがノードとして出る。ノードは「名前 ＋ 立ち位置 ＋ 識別色」
3. ノードの手動配置と、動かしたノードの座標の保存
4. 未配置ノードの決定的な既定配置（保存はしない）
5. 関係の追加 / ラベル編集 / 向きの変更 / 削除（ラベル自由テキスト・向き 3 値）
6. グループ枠の作成 / 名前編集 / キャラクターの割り当て・解除 / 削除（単層・1 キャラ 1 グループ）
7. 関係リスト（エッジ編集の代替経路。375px でエッジを選ぶ手段）
8. フォーカス表示（1 キャラクターの直接のつながりだけを表示）と全体表示の往復
9. パン・ズーム（表示のみ。倍率と位置は保存しない）
10. **375px でノード移動・結線・ラベル編集・グループ割り当てがすべて可能**であること
11. 旧 JSON（相関データ無し）の読み込み互換と、書き出しへの相関データ同梱
12. キャラクター削除 / グループ削除時の参照掃除と、キャラクター削除の確認文言の更新
13. キャラクター 0 人のときの案内（キャラクター管理ドロワーへの導線）

### 作らないもの（v1 スコープ外の宣言）

判断コストを下げるため明示する。以下が欲しくなったら、**本稿を更新してから**着手する。

- **シーン・場所をノードにする**（社長がスコープ外と確定。広げるには再決裁）
- **グループ枠の入れ子**、**1 キャラの複数グループ所属**
- エッジの線種 / 色 / 太さ / 強度による分類と、その凡例
- **`Scene.characterIds` からの自動線引き**、共演サジェスト、ノードからシーン一覧への導線
- ストーリー別の相関図、時点別（シーン進行に応じた）相関の変化
- 継続的な自動レイアウト（力学モデル等）、「配置をリセットして並べ直す」ボタン
- ズーム倍率・パン位置・表示モード・フォーカス状態の保存
- **図の画像書き出し / クリップボードへのコピー / 印刷 / PDF**
- 相関図の mermaid 等テキスト形式への書き出し（社長の依頼は逆方向）
- キャラクターの画像をノードに載せること
- 相関図側でのキャラクター本体（名前 / 立ち位置 / メモ / 識別色）の編集
- 「相関図に出さない」フラグ、ノードの表示 / 非表示の切替
- ノードの複数選択・一括移動・整列（揃える / 均等配置）
- 元に戻す（Undo / Redo）。既存機能にも無い
- エッジの重なり回避・曲線の自動整形といった高度な描画最適化
- 相関の他作品からのコピー・テンプレート
- 相関データの件数上限（サーバ版に載せる段で決める）

## 15. v2 / 将来

### v2（v1 が使われて価値が確認できたら）

- 共演（`Scene.characterIds`）からの関係サジェスト。「共演が多いのに線が無いペア」の提示
- ノード選択時に登場シーン数を出し、そのシーンへ飛べること
- エッジの線種・色による分類（凡例とセット）
- 図の画像書き出し / コピー（開放質問 Q5）
- ストーリー別の相関図
- 自動レイアウト（1 回きり実行する「整列」ボタン）
- 「相関図に出さない」フラグ（端役でノードが増えすぎたら）
- サーバ版（`accounts-and-server`）への載せ替えと、相関データの上限値の確定

### 将来（前提の再検討が必要）

- シーン・場所をノードにする（社長の確定スコープを広げる判断が要る）
- グループの入れ子・複数所属
- 時点別に変化する相関（**実日付を持たない設計に触れる**ため、プロダクトの前提の変更として扱う）
- キャラクターの画像（データモデルの拡張 ＋ 容量の検討）

## 17. 開放質問

**社長の回答が無くても design / dev は前進できる。**各項目に未回答時の既定を書いた。

| # | 優先 | 質問 | なぜ必要か | 未回答時の既定 |
| --- | --- | --- | --- | --- |
| **Q1** | 高 | 相関図に描きたいキャラクターは実際に何人規模か（10 人 / 30 人 / それ以上） | 375px の全体表示が成立するかの前提。既定配置アルゴリズムと、v2 の「相関図に出さない」フラグの要否にも直結する | **30 人前後で構造が読めること**を目標にする。上限は設けない（[6](#6-書き出し-json-への含め方と旧-json-互換論点-6)） |
| **Q2** | 高 | 関係は「ラベル 1 本」で足りるか。線種や色で分類したい（例: 血縁は実線、敵対は点線）か | 分類が必要ならエッジに属性が増え、凡例の面積も要る。375px の設計が変わる | **ラベルのみで進める**（[1](#1-関係エッジが持つ属性論点-1)）。分類は v2 |
| **Q3** | 中 | 1 キャラクターは 1 グループだけで足りるか。「〇〇家」かつ「騎士団」を同時に囲みたいか | 複数所属を許すと枠が重なり、図としても型としても複雑になる | **最大 1 グループで進める**（[7](#7-グループ枠の仕様入れ子可否の結論)）。二重の所属は関係（エッジ）で表現してもらう |
| **Q4** | 中 | スマホでの主用途は「作った図を見る」か「スマホで図を作る」か | 「作る」なら結線・配置の操作性に、「見る」ならフォーカス表示と可読性に、design の重心が変わる | **両方できる形で作る**。ただし精密な配置は PC が快適という前提で設計する（[8](#8-スマホ幅-375px-でどう成立させるか)） |
| **Q5** | 低 | 参照ビジュアルの「コピー」に相当する**図の画像書き出し**が要るか（相関図を storyline の外へ持ち出したいか） | 外部持ち出しの用途があるなら v1 に入れる価値が出る | **v1 では作らない**（[8](#8-スマホ幅-375px-でどう成立させるか)）。v2 候補 |
| **Q6** | 低 | 相関図の表示中にストーリータブを隠してよいか（相関図は本編 / 外伝を区別しないため） | 隠さない場合、タブが押せるのに図が変わらない状態になり誤解を生む | **隠す**（[5](#5-配置場所論点-5)） |

- 秘書決裁 **R-1**（本実装をどの土台に載せるか）は本稿で追認済み（[0](#0-この文書の位置づけ) 末尾）。
  企画部から新たに質問しない。
