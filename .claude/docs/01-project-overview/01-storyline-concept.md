# storyline プロダクト概要

シナリオの**構成 (時系列)** と**キャラクターのつながり**を整理するためのツール。
フロントエンドのみで動作し、データはブラウザの IndexedDB に保存される。

---

## 1. 何を解決するか

書き手が「話の順番」と「誰がどこに出てくるか」を同時に把握したいとき、テキストエディタでは
全体が見えず、汎用のカンバンツールでは物語の構造 (本編 / 外伝、章、シーン) に合わない。
storyline はその中間を埋める。

**やること**: 構成の一望・並べ替え・シーン単位のメモ・登場キャラの紐づけ
**やらないこと**: 本文の執筆、共同編集、クラウド同期、AI 生成

---

## 2. データ構造

```
作品 (Project)
├─ キャラクター (Character[])      … 作品共通。識別色を持つ
└─ ストーリー (Story[])            … 本編 / 外伝 などをタブで切り替え
   └─ シークエンス (Sequence[])    … カンバンの「列」
      └─ シーン (Scene[])          … カンバンの「カード」
```

定義は [src/lib/types.ts](../../../src/lib/types.ts)。

### 設計の核: 実日付を持たない

シーンは日付フィールドを持たない。**並び順そのものが時系列**で、`timeLabel`
(例: `事件当日 早朝`) は表示用の自由テキスト。これにより:

- 架空の暦・異世界の時間感覚でも破綻しない
- 回想・時系列シャッフルを「並べ替えずにラベルで示す」ことができる
- 日付計算・タイムゾーンの問題がそもそも発生しない

同じ理由で `order` フィールドも持たない (配列の順序が唯一の順序)。
**この設計を崩す提案は、プロダクトの前提の変更として扱う。**

### シーンが持つもの

| 項目 | 意味 |
| --- | --- |
| `title` / `summary` | シーン名とあらすじ |
| `characterIds` | 登場キャラクター (作品の `characters` への参照) |
| `timeLabel` / `place` | 時間ラベル・場所 (どちらも自由テキスト) |
| `status` | `idea` (プロット) / `draft` (執筆中) / `done` (完了) |
| `memo` | 自分用の覚え書き・伏線メモ |
| `thumbnail` | 任意。長辺 640px の JPEG data URL |

## 3. 画面

| 画面 | URL | 役割 |
| --- | --- | --- |
| 作品一覧 | `/` | 作品の作成・削除・書き出し・読み込み。統計と更新日時を表示 |
| 作品画面 | `/projects/<id>` | ストーリータブ + カンバン + 各種ドロワー |

作品画面の構成:

- 上部: 作品名・ログライン (インライン編集)、キャラクター一覧を開くボタン、書き出し
- タブ: ストーリー切替 / 追加 / 並べ替え / 削除
- 本体: シークエンス列 × シーンカードのカンバン (ドラッグ & ドロップ)
- 右からのドロワー: シーン編集 / キャラクター管理

---

## 4. 技術的な前提 (企画判断に効く制約)

| 前提 | 意味すること |
| --- | --- |
| **サーバが無い** | 同期・共同編集・共有リンク・アカウントは実装できない (作り直しに近い) |
| **データは IndexedDB のみ** | ブラウザのサイトデータ削除で消える。バックアップは JSON 手動書き出し |
| **AI 機能が無い** | 依存も API キーも無い。入れるならサーバ前提が新たに必要 |
| **端末間の移動は JSON** | `*.storyline.json` の書き出し / 読み込みが唯一の移行手段 |

スタック: Next.js 16.3 (App Router) / React 19.2 / TypeScript 5 / zustand 5 + immer /
idb-keyval / dnd-kit / Tailwind v4。デプロイは Vercel。

> **注意 (2026-08-04)**: この表の前提のうち「サーバが無い」「データは IndexedDB のみ」は、
> アカウント制 + サーバへの移行が決裁済みのため、移行完了時点で変わる
> ([決裁記録](../../.company/secretary/decisions/2026-08-04-accounts-and-server-decisions.md))。
> 現行コードはまだローカル完結であり、移行が終わるまでは本ドキュメントの記述が現状を表す。

## 5. 想定利用者と優先順位

まず **作者自身**が使う個人ツール。判断に迷ったら次の順で優先する:

1. **書く手を止めないか** — 構成を考える流れを中断させる機能は価値が低い
2. **一望性を損なわないか** — カンバンで全体が見えることがこのツールの本体
3. **データを増やす価値があるか** — 項目追加はカードの情報密度を上げ、可読性を下げる
